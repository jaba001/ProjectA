## 게임의 정체성

**파티 전체를 성장시키며 매 Run마다 빌드를 만들고, 다른 플레이어의 Party Snapshot을 상대로 직접 전술 전투를 진행하는 협동 로그라이크**를 목표로 한다.

| 핵심 | 플레이 경험 |
|---|---|
| 파티 빌드 | 직업·장비·스킬·역할을 조합하고 파티 전체를 성장시킨다 |
| 로그라이크 Run | 선택과 보상이 누적되어 매번 다른 빌드를 만든다 |
| Async PvP | 상대의 동시 접속 없이 저장된 상대 파티와 싸운다 |
| 직접 조작 Grid 전투 | 플레이어가 이동·배치·타겟·스킬 사용을 판단한다 |
| 아군 Co-op | 친구와 자신의 캐릭터를 조작하며 같은 파티를 운영한다 |

For The King에서는 파티 구성·역할 분담·누적 자원 관리·협동을, The Bazaar와 Backpack Battles에서는 비동기 상대 빌드를 참고한다. UI에서 빠르게 선택하고 전투로 이어지는 흐름을 지향한다. 참고작의 전체 시스템을 복제하는 계획은 아니다.

판단 기준은 **단위 시간당 의미 있는 선택의 양(Decision Density)**이다. 장비를 줄 대상, 스킬 조합, 상대에 따른 배치, 공격 순서와 자원 사용을 고민하게 한다. 반복 이동·긴 카메라 전환·결과가 정해진 잔여 턴·다른 사람의 메뉴 조작 대기를 늘리는 기능은 피한다.

## 목표 Run과 현재 구현

```text
파티 생성 → Run 시작 → 선택 UI
→ 상점 / 이벤트 / 훈련 / 강화 / 회복
→ 상대 확인과 전투 준비 → Async PvP 전투
→ 결과 → 보상과 파티 강화 → 다음 Round
→ 최종 Encounter → Run 결과
```

위 흐름은 목표다. 현재는 `MainMenu → CharacterCreation → Gameplay → Run Map UI → Combat → Victory / Continue → 다음 노드`의 두 순차 전투를 제공하며, **패배 시 Run을 종료한다**. 패배 이후에도 진행할지와 보상을 어떻게 줄지는 아직 정하지 않았다.

| 영역 | 현재 구현 | 확장 목표 |
|---|---|---|
| 성장 | 이름·직업·HP·노드 진행 보존 | 장비·스킬·보상이 누적되는 파티 빌드 |
| 스킬·아이템 | 추가 스킬과 회복약을 전투마다 지급 | 획득·장착·소모·강화의 Run 단위 규칙 |
| 상대 | PvE와 로컬 Snapshot Encounter, 적 AI | 온라인 상대 Build·Formation·Tactics |
| 협동 | 개발 환경의 Listen Server, 턴 복구·승계·AI | 실제 계정·초대·P2P·공유 저장 연결 |
| 경쟁 | MMR 방향만 확정 | 인증된 결과와 정산·매칭 정책 |

로컬 멀티플레이 구현과 검증 이력은 [HISTORY](HISTORY.md)에 있다. 최신 수정의 작동 확인은 사용자가 [TEST_REPORT](TEST_REPORT.md)에 따라 수행하며, 온라인 서비스 완료로 해석하지 않는다.

## UI 중심 진행과 전투

물리적인 WorldMap 탐험은 사용하지 않는다. 월드 이동 포인트, 상점까지 걸어가기, 플레이어별 월드 이동 턴, 넓은 절차 생성 월드와 파티의 물리적 분산은 현재 범위에서 제외한다. 필요하면 간단한 Node Map 또는 Timeline/Progress UI로 진행을 표현한다.

지역 배경·음악·Arena·상대 Pool·상점·이벤트를 바꾸어 여행과 성장의 감각을 만든다. Act 구성, Round 수, 목표 플레이 시간은 예시 단계이며 확정 수치가 없다.

현재 Grid·Turn·Movement·Targeting·Skill·GAS 전투를 유지한다. 작은 4×4 Grid를 기획 출발점으로 삼고, 짧은 전투에서도 공격·방어·지원·회복 역할이 기여하게 한다. 긴 이동·애니메이션·과도한 HP가 만드는 대기는 사용자의 플레이 결과로 판단한다.

## 상대 Snapshot과 전술

상대의 파티 구성·Class·Stats·Skills·Equipment·Formation·데이터 버전을 직렬화하고, 해당 Snapshot으로 생성한 상대를 AI가 조작한다. 향후 Tactics도 포함할 수 있게 한다. PvE와 같은 Unit/Combat 흐름을 우선하고 Actor 자체를 저장하지 않는다.

첫 단계는 로컬 USaveGame Snapshot 전투다. 현재 장비·전술 식별자는 저장 구조만 있으며 실행은 빈 값만 지원한다. 낮은 HP/전열/후열 우선 공격, 공격적/방어적/지원 성향, 스킬 우선순위는 **후속 전술 기획의 예시**다. 편집 UI·평가 규칙은 아직 구현 범위가 아니다.

경쟁 콘텐츠에서는 상대 데이터와 결과 검증을 별도로 설계한다. 내 전투가 상대 소유자의 성적에도 영향을 줄지는 미정이다. 저장 형식과 지원 제한은 [MULTIPLAYER](MULTIPLAYER.md)에 한 번만 정의한다.

## 협동 확정 정책

- 최대 4명이 접속한다. 자신의 캐릭터는 원래 소유자만 인간 조작하며 같은 Run에 다른 사람이 대체 참가하지 못한다.
- 최초 Host는 1번, 이후 합류자는 2·3·4번을 유지한다. 명시적 재개에 참여하는 인간 중 가장 작은 번호가 Host를 승계한다.
- 정상 종료·돌발 끊김만으로 Host나 AI 모드를 바꾸지 않는다. 원래 참가자가 명시적으로 이어하기를 선택한다.
- AI 전환은 **개인 사전 동의 없이 Host가 단독 결정**한다. 싱글 전환 시 본인이 Host가 되고 나머지는 Run 종료까지 AI다. 원래 소유자가 돌아와도 인간 조작으로 되돌리지 않는다.
- Host 승계와 캐릭터 소유권은 별개다. 새 Host도 다른 사람의 캐릭터를 직접 조작하지 못한다.
- 현재 Host가 다음 노드와 승리 후 Continue를 결정한다. 복구 시점은 마지막 확정 턴 경계다.
- AI 전환 후 MMR은 현재 인간 참가자에게만 반영하고 불참자에게 추가 변동을 주지 않는다. 정산 시점·계산·이탈 악용 대응은 미정이다.
- Unreal Listen Server와 Steam P2P를 우선한다. 선택한 Steam+PlayFab은 운영비를 피하려는 조건 안에서 검토하며 유료 리소스를 임의로 활성화하지 않는다.

각자 장비·스킬을 동시에 관리하고 Ready 후 다음 단계로 가는 UX를 선호한다. 공동 재화·장비 배분, Ready 대기·이탈 처리, 1인당 보유 캐릭터 수, 캐릭터 부족 시 배정, 돌아온 AI 소유자의 관전 허용은 추가 결정이 필요하다.

## 구현 원칙과 다음 콘텐츠

기본 Run은 싱글플레이를 유지한다. 전투마다 OpenLevel하지 않고 같은 Gameplay persistent level에서 Encounter를 교체한다. Level Instance/Streaming은 실제 콘텐츠 요구가 생기면 검토한다. Run/Party/Encounter/Combat의 장기 데이터는 직렬화 가능한 Runtime Data와 Command를 사용하고, Actor·Controller·Widget·Ability 인스턴스는 실행 중 표현과 연결을 맡긴다.

기존 Vertical Slice 유지 → Run의 의미 있는 선택 확장 → 필요한 공통화와 네트워크 확장 순서로 진행한다. 전체 Replication 전환·즉시 자동 Host Migration·Dedicated Server·복잡한 월드 생성은 일괄 착수하지 않는다. 실제 인증·중앙 저장·랭킹·매칭은 T14의 후속 단계다.

가장 작은 다음 콘텐츠 제안은 **전투 → 보상 선택 → 적용할 파티원 선택 → Run에 보존 → 다음 전투에서 활용**이다. 상점·이벤트·훈련·휴식·강화·상대 미리보기도 하나씩 추가한다. 보상 후보 수·종류·전투 수는 승인된 구현 사양이 아니다.

사용자 검증에서는 빌드 선택이 다음 전투의 판단을 바꾸는지, 승패 이유를 조합과 행동으로 설명할 수 있는지, AI 실수 공략만 반복되는지, 협동 의논보다 대기가 길어지는지 확인한다. 세부 결정과 착수 순서는 [TODO](TODO.md)에만 관리한다.
