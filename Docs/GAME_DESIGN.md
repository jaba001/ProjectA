# ProjectA 게임 기획 방향

정리일: 2026-09-10

사용자가 공유한 「ProjectA 게임 기획 방향」을 정리한 문서다. 현재 Vertical Slice를 유지하면서 이후 기능과 구조 개선을 판단하는 기획 기준으로 사용한다. 목표 기능을 구현 완료로 취급하지 않으며, 예시에 등장하는 Round 수·시간·전술 옵션은 확정 수치가 아니다. 마지막 절의 검증 제안과 미결정 정책은 확정된 개발 작업과 구분한다.

## 1. 게임의 핵심 정체성

> 파티 전체를 성장시키며 매 Run마다 빌드를 완성하고, 다른 플레이어가 만든 파티 Snapshot을 상대로 직접 전술 전투를 진행하는 협동 로그라이크를 목표로 한다.

| 구성 | ProjectA에서의 역할 |
|---|---|
| Co-op Party Builder | 친구와 같은 파티를 운영하며 직업·장비·스킬·역할을 조합한다 |
| Roguelike Run | 매 Run의 선택과 보상으로 서로 다른 파티 빌드를 만든다 |
| Async PvP | 상대의 동시 접속 없이 다른 플레이어의 Party Build Snapshot과 싸운다 |
| Direct Tactical Grid Combat | 플레이어가 이동·배치·타겟·스킬을 직접 판단하고 조작한다 |

빌드 과정과 직접 전술 전투를 모두 핵심 재미로 둔다. 한 캐릭터의 성장뿐 아니라 **파티 전체를 키우는 감각**을 중요하게 본다. 최종적으로 PvE 중심 진행보다 Async PvP를 핵심 경쟁 콘텐츠로 삼되, 현재는 싱글플레이 루프와 콘텐츠를 먼저 검증한다.

## 2. 참고 게임에서 가져올 요소와 제외할 요소

아래 내용은 사용자 기획에서 선택한 참고 요소이며, 각 게임의 전체 시스템을 복제하는 계획이 아니다.

| 참고 방향 | 가져올 요소 | 적용 범위 |
|---|---|---|
| For The King 계열 | 여러 캐릭터의 파티, 직업 조합, 역할 분담, 장비·스킬 조합, 누적 체력·자원 관리, 친구와의 협동 | 파티 운영과 Run 성장의 재미 |
| The Bazaar / Backpack Battles 계열 | 다른 플레이어의 빌드와 비동기로 대결하는 구조 | 상대 Snapshot 활용. ProjectA 전투는 직접 조작 유지 |
| The Bazaar / Grail 계열 | UI에서 선택하고 빠르게 다음 단계로 진행하는 방향 | Run 진행 화면과 선택의 밀도 |
| Slay the Spire 스타일 Node Map | 진행 경로와 선택지를 시각화하는 방식 | 필요할 때 검토할 선택지. 복잡한 노드 생성은 필수 아님 |

물리적인 WorldMap 탐험은 사용하지 않는다. 다음 요소를 새로 구현하지 않는다.

- 육각형 월드맵 직접 이동, 이동 포인트 소비, 목적지까지 여러 턴 이동
- 상점·이벤트까지 걸어가는 과정과 플레이어별 월드 이동 턴
- 넓은 절차 생성 월드와 파티가 월드에서 물리적으로 흩어지는 시스템

월드 생성·경로·카메라·이벤트 배치·지역 관리의 개발 비용을 줄이고, 선택·강화·전투·보상의 밀도를 높이는 데 집중한다.

## 3. 가장 중요한 판단 기준: Decision Density

**단위 시간당 의미 있는 선택이 많은 게임**을 목표로 한다. 플레이 시간이 늘어나는 것 자체를 목표로 삼지 않는다.

| 늘리고 싶은 경험 | 줄이고 싶은 시간 |
|---|---|
| 구매할 장비와 장비를 줄 파티원 선택 | 상점이나 목적지까지 반복 이동 |
| 스킬·직업·파티 조합 선택 | 긴 카메라 이동과 전투 사이 OpenLevel 로딩 |
| 상대 조합에 따른 배치 변경 | 다른 플레이어의 메뉴 조작 대기 |
| 공격 우선순위와 스킬 사용 순서 판단 | 의미 없는 적 애니메이션 대기 |
| 지금 자원을 쓸지 다음 전투를 위해 아낄지 판단 | 결과가 사실상 정해진 전투의 불필요한 잔여 턴 |

새 기능은 다음 질문으로 판단한다.

> 이 기능이 플레이어에게 새로운 의미 있는 결정을 제공하는가, 아니면 플레이 시간을 늘리기만 하는가?

## 4. 목표 Run Loop

```text
파티 생성 → Run 시작
→ 선택 UI
→ 상점 / 이벤트 / 훈련 / 강화 / 회복 등
→ 상대 파티 확인 및 준비
→ 비동기 PvP 전투
→ 승리 / 패배 결과
→ 보상 및 파티 강화
→ 다음 Round에서 더 강한 상대와 대결
→ 최종 Encounter
→ Run 결과
```

이 흐름은 최종 목표이며, 현재 구현된 싱글플레이 흐름과 구분한다. 원문에는 승리·패배 뒤 보상과 다음 Round로 이어지는 흐름이 포함되어 있다. 패배 후 진행 허용 조건, 보상 차이, Run 종료 기준은 추가 결정이 필요하다. 현재 구현은 패배 시 Run 종료를 유지한다.

전투와 전투 사이에 의미 없는 이동이나 긴 전환을 넣지 않는다. 성장 선택이 다음 전투의 행동을 바꾸고, 전투에서 확인한 강점과 약점이 다음 성장 선택으로 이어지도록 설계한다.

## 5. UI 중심 진행과 여행의 감각

Run 진행은 CommonUI 화면에서 표현한다. 별도의 WorldMap gameplay level을 다시 만들지 않는다.

```text
RUN — Round 3 / 10

[상점] [이벤트] [훈련] [회복]

선택 → 다음 상대 확인 → 전투
```

Timeline / Progress UI만으로도 진행할 수 있다. Node Map을 사용하더라도 복잡한 월드맵이나 절차 생성 노드 그래프를 전제로 하지 않는다. 핵심은 UI에서 의미 있는 선택을 하고 빠르게 다음 Encounter로 들어가는 것이다.

물리적인 WorldMap 없이도 Run이 진행되고 여행하고 있다는 감각은 유지한다.

```text
ACT 1 — Forest, Round 1 / 5
→ ACT 1 — Forest, Round 4 / 5
→ ACT 2 — Ruins, Round 1 / 6
```

지역별 배경·음악·Encounter Arena·상대 Snapshot 또는 적 구성 Pool·상점 내용·Event Pool로 진행감을 표현할 수 있다. Act 구성과 Round 수는 예시이며, 콘텐츠가 필요해질 때 구체화한다.

## 6. 직접 조작 전투와 템포

현재의 Grid·Turn·Movement·Targeting·Skill·GAS 기반 전투를 유지한다. 플레이어는 빌드를 만든 뒤 실제 전투에서도 직접 전술적으로 조작한다.

- 현재 4×4 Grid처럼 작은 전투 공간을 기획의 출발점으로 사용한다.
- 일반 Encounter는 짧고 밀도 있게 진행하는 것을 목표로 한다.
- 긴 이동·애니메이션·불필요한 턴 대기·과도한 HP 증가가 템포에 미치는 영향을 확인한다.
- 정확한 Encounter 시간과 Run 길이는 플레이 테스트로 결정한다.

## 7. Async PvP와 상대 Snapshot

상대 플레이어가 동시에 접속해 있을 필요가 없는 비동기 PvP를 목표로 한다.

```text
다른 플레이어의 Party Build
→ 직렬화 가능한 Snapshot으로 서버에 저장
→ 내 Run 진행에 맞는 상대 Snapshot 획득
→ 내 Encounter에서 상대 파티 생성
→ 직접 조작 전투
→ 결과 기록
```

Snapshot이 향후 표현할 수 있어야 할 데이터는 다음과 같다. 아래는 설계 대상이며 현재 구현된 저장 스키마가 아니다.

| 데이터 | 내용 |
|---|---|
| Party Composition / Class | 파티 구성, 직업 식별자 |
| Stats | 전투에 필요한 능력치 |
| Skills / Equipment | 스킬·장비 식별자와 빌드 구성 |
| Formation | 전투 시작 배치 |
| Tactics | 후속 전술 성향과 우선순위 |
| Data Version | 데이터 해석과 호환 여부를 판단할 버전 |

월드 Actor 자체를 저장하지 않는다. PvE Encounter와 Snapshot Encounter는 가능한 한 같은 Unit/Combat 흐름을 사용한다.

초기에는 로컬 Snapshot으로 전투를 검증할 수 있다. 경쟁 콘텐츠로 제공하기 전에는 서버의 데이터·결과 검증과 위변조 대응 정책을 별도로 설계한다. 로컬 Snapshot 전투나 일부 복제 선언만으로 온라인 경쟁 콘텐츠가 완성됐다고 기록하지 않는다.

## 8. 상대 AI와 플레이어가 설정하는 전술

비동기 상대의 캐릭터는 AI가 조작한다. 향후에는 장비·스탯뿐 아니라 플레이어가 정한 전술 성향도 Snapshot에 담는 구조를 고려한다.

| 전술 종류 | 예시 |
|---|---|
| Target Priority | 낮은 HP, 전열, 후열, 특정 직업 우선 |
| Behavior | 공격적, 방어적, 지원 중심 |
| Skill Priority | Skill A → Skill B → 기본 공격 |

목표는 **Build + Formation + Tactics**를 통해 상대가 오프라인이어도 다른 플레이어가 만든 파티와 싸우는 느낌을 강화하는 것이다. 전술 편집 시스템은 후속 기획이며 즉시 구현하지 않는다.

## 9. 아군 Co-op과 협동 UX

최종 목표는 **아군은 실시간 Co-op, 적군은 Async PvP**인 구조다.

```text
Player A + Player B가 함께 운영하는 우리 파티
vs
AI가 조작하는 다른 플레이어의 Party Snapshot
```

위 인원은 설명용 예시이며 최대 접속 인원은 미정이다. 플레이어는 자신에게 할당된 Party Member만 조작한다.

Unreal의 Listen Server 기반 Host-authoritative 구조를 우선한다. Steam/EOS 등의 P2P transport를 검토할 수 있지만 게임플레이 권위는 Host/Server가 가진다. 서버가 Action Request를 검증·실행하고 CombatManager·TurnManager·Grid Occupancy·Unit State·HP/AP·사망·Combat Result의 최종 권위를 갖는다.

협동 중에는 각자 자기 캐릭터의 장비·스킬을 동시에 관리하고, 준비가 끝나면 Ready 상태가 되며, 모두 준비되면 다음 단계로 진행하는 UX를 선호한다.

공동 재화·장비 배분·파티 공통 선택의 결정권은 아직 미정이다. 구체적인 Ready 대기·이탈 처리 규칙도 후속 결정 사항이다.

## 10. 유지할 레벨 구조와 데이터 원칙

현재 구현한 다음 구조를 유지한다.

```text
MainMenu → CharacterCreation → Gameplay Persistent Level
→ Run Map UI → Encounter → Combat → Result → Run Map UI
```

위 반복 경로는 현재 승리 후 Continue 흐름에 해당한다. 현재 패배 결과는 Run 종료로 이어진다.

- 전투마다 OpenLevel하지 않는다.
- Arena 변경은 같은 Gameplay level 내부 구조를 우선한다.
- Level Instance / Streaming은 콘텐츠 규모와 실제 요구가 생겼을 때 검토한다.
- Run/Party/Encounter/Combat의 장기 데이터는 직렬화 가능한 Runtime Data와 Command를 우선한다.
- 강한 로컬 PlayerController 의존성을 새로 만들지 않는다.

| 장기 데이터로 관리할 정보의 예 | 장기 데이터에 저장하지 않을 World reference의 예 |
|---|---|
| PartyMemberData, ClassId, Stats, SkillIds, ItemIds, Formation, Tactics, HP | `APlayerUnit*`, `ACombatManager*`, `APlayerController*`, `UWidget*`, `UGameplayAbility` instance |

Actor는 Run/Encounter 데이터를 월드에 표현하는 Runtime Instance로 취급한다. Actor와 위젯 참조가 필요한 실행 중 연결과, 저장·Snapshot·향후 Replication을 위한 데이터의 책임을 구분한다.

## 11. 단계적으로 추가할 콘텐츠

상점, 이벤트, 훈련, 휴식, 스킬 강화, 장비 강화, 위험/보상 이벤트, 상대 미리보기, 보상 선택을 Encounter 사이의 UI 콘텐츠로 사용할 수 있다.

모든 기능을 한 번에 구현하지 않는다. 현재 싱글플레이 Vertical Slice 위에서 직업·빌드·상점·보상·Encounter 다양화·Run 진행을 하나씩 추가하며 게임의 재미를 검증한다.

## 12. 개발 우선순위와 현재 제외 범위

기능 구현과 구조 개선은 다음 순서로 판단한다.

1. 현재 Vertical Slice를 깨지 않는다.
2. 실제 게임 Loop를 확장한다.
3. 플레이어의 의미 있는 선택을 늘린다.
4. 불필요한 월드/레벨 시스템을 만들지 않는다.
5. Async PvP에 사용할 수 있도록 Party/Build 데이터를 Actor와 분리한다.
6. 향후 Co-op을 방해하는 강한 로컬 PlayerController 의존성을 새로 만들지 않는다.
7. 네트워크 전체 구현을 위해 현재 싱글플레이 구조를 미리 대규모 리팩터링하지 않는다.
8. 실제 콘텐츠 요구가 생겼을 때 필요한 공통화와 네트워크 확장을 진행한다.

현재 즉시 구현하지 않을 항목:

- 전체 Replication 전환, Steam/EOS Lobby, Host Migration
- Backend, Matchmaking, Async Snapshot Server
- Dedicated Server, Ranking, Anti-Cheat
- Procedural WorldMap, Open World, 복잡한 Node Generator

멀티플레이는 최종 목표로 유지하며, 본격 구현 시점은 게임 Loop가 더 구체화된 이후로 잡는다.

| 패배 | Run 종료 | 패배 후 진행·보상·최종 종료 조건 구체화 필요 |
| 상대 | 현재 PvE Encounter와 적 AI | 다른 플레이어의 Build/Formation/Tactics Snapshot |
| 멀티플레이 | 싱글플레이, T14 기획 확정 / 구현 후속 | Async PvP와 Listen Server Co-op |

## 14. 후속 결정과 작은 검증 제안

다음 항목은 검토 메모다. 확정된 기획이나 즉시 착수할 작업으로 취급하지 않는다. 구현이 해당 결정에 의존할 때 선택지와 영향을 사용자에게 확인한다.

| 미결정 항목 | 선택지와 영향 |
|---|---|
| 패배 후 Run 진행 | 즉시 종료는 한 전투의 긴장감을 높인다. 패배 횟수나 Run 생명력 방식은 빌드를 더 이어갈 여지를 준다 |
| 누적 HP·사망·회복 | 손실 유지는 자원 관리의 무게를 높인다. 전투 전 회복·정규화는 상대와 비교할 전투 조건을 맞추기 쉽다. Snapshot의 전투 시작 HP·소모품 상태와 저장 시점도 함께 결정한다 |
| 공격·방어 결과의 의미 | 내 Run에만 결과를 반영하면 도전 흐름을 먼저 검증할 수 있다. 상대 소유자의 성적에도 반영하면 방어 AI와 결과 집계 규칙이 필요하다 |
| Co-op 재화·장비 배분 | 공동 재화·합의 구매는 파티 운영의 협동성을 높인다. 개인 예산·개별 구매는 동시에 진행하기 쉽다 |
| 플레이어 수·조작권 | 최대 접속 인원과 한 플레이어가 맡을 Party Member 수를 정해야 한다 |
| 플레이 흐름과 정보 | 목표 시간·Round 수·최종 Encounter 조건, 상대 사전 공개 범위, Ready 대기·이탈 처리 규칙을 정해야 한다 |
| 빌드와 전술 상세 | 성장·스킬·장비의 지속 범위와 구체적인 Tactics 옵션·평가 규칙을 정해야 한다 |
| 네트워크 서비스 정책 | Host disconnect, Steam/EOS, Lobby/Invite, Backend·매칭, Snapshot 저장 포맷·버전 호환, 데이터·결과 검증은 T14의 후속 결정 사항이다 |

가장 작은 후속 검증 제안은 **전투 보상 선택이 다음 전투의 플레이를 바꾸는 짧은 싱글플레이 Run**이다.

```text
전투 → 강화 후보 선택 → 적용할 파티원 선택
→ 선택 결과를 Run 데이터에 유지 → 다음 전투에서 활용
```

여기에 성격이 다른 로컬 상대 Snapshot을 추가하면 네트워크 서비스 구현에 앞서 다른 파티 빌드를 상대하는 경험을 확인할 수 있다. 구체적인 후보 수·보상 종류·전투 수는 제안 단계다.

확인할 질문:

- 빌드 선택이 다음 전투의 배치·타겟·스킬 사용을 실제로 바꾸는가?
- 승패 이유를 상대 조합과 내 판단으로 설명할 수 있는가? 반복되는 AI 실수 공략이 상대 빌드의 존재감을 약하게 만들지 않는가?
- 지원·방어·회복 역할도 짧은 전투에서 기여할 기회가 있는가?
- 의미 있는 고민보다 반복 입력·이동·애니메이션 대기가 길어지지 않는가?
- 협동 역할을 나눠 플레이할 때 함께 의논하는 시간과 할 일 없이 기다리는 시간은 어떻게 다른가?

이 제안의 착수와 세부 규칙은 다음 작업에서 결정한다. 현재 구현 상태와 검증 결과는 계속 [작업 보드](TODO.md)에 별도로 기록한다.
