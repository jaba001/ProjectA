작동 테스트는 사용자 수행이 원칙이며 명시적 요청에 한해 Codex가 실행한다. 컴파일·정적 검사와 작동 검증을 구분하며 미실행 항목은 완료로 표시하지 않는다.

## 준비 조건

- UE 5.7에서 최신 소스와 빌드된 `ProjectAEditor`를 사용한다. C++·리플렉션 전환 후 UE를 재시작한다. 새 라운드 화면에 별도 WBP/맵 생성·Config 변경은 필요하지 않다. Visual Studio 실행은 필요하지 않다.
- 일반 플레이 확인은 `/Game/User_JeHoon/LEVEL/MainMenu`에서 시작한다. 프로젝트 기본 설정과 에셋 경로는 [PROJECT_PLAN](PROJECT_PLAN.md)을 따른다.
- 게임 시작에서 싱글플레이를 선택하면 일반 파티를 생성한다. 멀티플레이는 같은 PC·LAN의 기존 개발용 방이다. **관리 Run의 협동 생성·참가 번호 선택·실제 Steam 로그인 UI는 아직 없다.** 관리 이어하기 패널은 C++ 개발 fixture가 호출자와 저장 대상을 설정해야 표시된다.
- 첫 화면의 별도 개발용 협동 버튼은 제거했으며 **게임 시작 → 멀티플레이**로 새 비관리 방 생성·주소 접속을 연다. 9절의 수동 절차를 사용하며 2절의 관리 저장·승계를 대체하지 않는다.
- 아래 이전 관리/턴 복구 시나리오는 당시 fixture의 이력이다. 현재 Combat 복원은 거절되며 지원되는 비전투 재개·무변경 거절 검증은 12절을 따른다. 실제 친구 초대·다른 PC·Steam 인증 시험과 구분한다.
- 일반 새 게임은 기존 단일 진행 슬롯을 갱신한다. 보존할 세이브가 있으면 실행 전에 `Saved/SaveGames`를 별도 위치에 복사한다. 관리 fixture는 고유 namespace/Run ID를 사용한다.

## 1. 직접 플레이 확인

목적은 최신 코드에서 **새 게임 → 첫 전투 → 결과 → 상점 선택·진입·퇴장 → 두 번째 전투와 설정 변경·복원**을 사용자가 한 번에 확인하는 것이다. 이번 점검은 저장 실패 복구·파티 사전 검사·Cue 설정을 대상으로 했으며, 아래 실행은 모두 미실행이다.

최신 Development Editor / Win64 빌드 후 기존 UE를 종료하고 [14-2의 사용자 실행 명령](#14-2-준비-조건)으로 독립 게임 창을 연다. 보존할 `Saved/SaveGames`와 사용 중인 `GameUserSettings.ini`는 먼저 백업한다. **게임 시작 → 싱글플레이**로 시작하며 기존 Continue·협동 방을 사용하지 않는다. 새 맵·WBP 생성과 설정 재연결은 필요 없다.

이 통합 확인은 저장 실패 주입·Cue 실제 로딩·에디터 데이터 검사를 대신하지 않는다. 실패 복구는 [18절](#18-준비-취소-복구와-파티-데이터-사전-검사), Cue는 [8절](#8-hudgameplaycue-경고-수정), 상세 피격은 [19절](#19-서버-공격-충돌-판정), 설정은 [14절](#14-시작-메뉴-화면그래픽-설정)을 따른다. 이후 **2인 협동 → 4인 협동** 순서로 [9절](#9-개발용-협동-ui)을 진행한다.

## 2. 승계 검증

사용자 명시 요청으로 당시 순차 전투의 2-1~2-3을 실행했다. 아래 명령·수용 결과는 과거 재현 기록이며 현재 Combat 복구 경로에 적용하지 않는다. 해당 순차 PIE fixture는 현재 소스에서 제거했으며 명령은 Git 이력의 당시 코드에만 적용한다. 최신 실행 지침은 12절이다.

```powershell
$reportPath = Join-Path (Get-Location) ('Saved/Automation/UserManagedRun_' + (Get-Date -Format 'yyyyMMdd_HHmmss'))
& 'C:/Program Files/Epic Games/UE_5.7/Engine/Binaries/Win64/UnrealEditor-Cmd.exe' 'C:/Users/jaba0/Desktop/MyProjects/ProjectA/ProjectA.uproject' -unattended -nop4 -RenderOffscreen -nosound -T14ManagedRunPIE '-ExecCmds=Automation RunTests ProjectA.ManagedRunPIE.' '-TestExit=Automation Test Queue Empty' "-ReportExportPath=$reportPath"
```

테스트 코드가 세션·행동을 구동한다. 에디터에서는 `-T14ManagedRunPIE`로 시작 후 Session Frontend → Automation → `ProjectA.ManagedRunPIE.` 3개를 선택한다. 전용 인자가 없으면 실제 검증 없이 종료된다.

## 12 시간차 자동 전투 기획 검토

### 12-1 목적과 대상

기본 Gameplay의 순차 전투를 계획·시간차 실행으로 교체한 결과를 확인한다. 대상은 CombatManager/RoundCoordinator·계획 Controller/CommonUI·스킬 프로필·실제 이동/피격·Encounter 결과·이전 저장 거절과 관련 테스트다. 기준 기획은 [GAME_DESIGN 8절](GAME_DESIGN.md#8-라운드-계획과-시간차-자동-전투), 미확정 정책은 [TODO 3-1절](TODO.md#3-1-전투-규칙), 네트워크/저장 경계는 [MULTIPLAYER 12절](MULTIPLAYER.md#12-시간차-자동-전투의-확장-경계)다.

현재 기본값인 복귀 칸 예약 충돌 거절·같은 시각 서버 순서·팀원 계획 수정 시 인간 Ready 전체 해제는 사용자 확정 정책이 아니다. 검증 결과와 함께 최종 채택 여부를 확인한다. 양 팀 전멸은 Suspended로 중단하며 Run 결과가 확정되지 않는 제한이 있다.

### 12-2 준비 조건과 실행 절차

최종 Editor 빌드를 적용하고 UE를 재시작한다. MainMenu → 게임 시작 → 싱글플레이 → 캐릭터 생성 → Gameplay → 첫 Combat로 진입한다. 새 맵·WBP 생성과 Config 변경은 필요하지 않다. 기존 순차 HUD 대신 계획 화면이 나타나야 한다. 오른쪽에서 아군/스킬/대상/목적지 선택 → 계획 적용 → 인간 조작이 허용된 모든 생존 아군 지정 → 준비 완료 순서로 진행한다.

속도 시험은 별도 검증 fixture에서 GAS `Dexterity`를 20·19·15·10으로 준비한다. 독립 `CombatSpeed` 값은 사용하지 않는다. 현재 기본 아군 민첩/속도는 10, 일반 적은 5이므로 기본 첫 라운드의 적 시작 지연은 0.5초다. 소수 민첩·라운드 고정·Snapshot 확인은 [24절](#24-민첩-기반-전투-속도와-일반-적-능력치)을 따른다. 스킬 상세 시험은 `bUseRoundDefinition`과 `RoundDefinition`을 사용하며 원본 콘텐츠를 바꿀 경우 작업 사본은 `/Game/User_JeHoon/`에 둔다. 공통 Guard/Wait/MoveShot/GroundStrike와 기존 장착 스킬 초기 변환은 시험값이다. 실제 두 사람 검증은 9절의 개발용 새 방으로 진행한다.

### 14-4 개발 확인과 제한

Development Editor / Win64의 기능 변경 빌드가 성공했다(18.45초, `Saved/Logs/OptionsSettingsBuild.log`). 메뉴 회귀 코드 보강을 포함한 최종 증분 빌드도 성공했다(3.88초, `Saved/Logs/OptionsSettingsFinalBuild.log`). 두 빌드 모두 컴파일 오류·경고 0이며 설정 확인·복원·수명 정리 경로와 테스트 코드를 정적으로 검토했다.

[기존 메뉴 회귀 코드](../Source/ProjectAEditor/Tests/VerticalSliceFlowTests.cpp)에 초안 취소·재진입, 화면 모드별 해상도 선택 가능 여부, 품질/VSync 저장, 사용자 Landscape·렌더 배율의 보존과 명시적 프리셋 선택을 추가했다. 컴파일과 코드 검토만 수행했으며 해당 회귀 테스트의 실행 결과는 없다.

변경 문서 5개의 로컬 링크 83개·앵커 39개·코드 블록 닫힘과 14절 검증 ID 17개의 유일성·미실행 표기를 검사했다. PIE·게임 플레이·자동화 테스트·패키지 실행은 수행하지 않았다. 기존 T11 옵션 및 라운드 전투의 성공 기록은 이번 화면 변경·복원 성공 근거로 사용하지 않는다.

실패·경고는 사용자 작동 검증 전이므로 미확인이다. 확인 중 화면이 보이지 않으면 입력하지 않고 15초 복원을 기다린다. 복원 또는 재시작 저장이 실패하면 OS 해상도·배율·창 모드·변경 전후 값·최초 실패 단계·로그를 기록하고 해당 설정 변경을 보류한다. 사용자 결과가 오기 전에는 위 항목을 완료로 변경하지 않는다.

## 15. DemonicUI 공통 테마

### 15-1 목적과 대상 변경

기존 DemonicUI 외형 적용 후 가독성·버튼 상태·화면 전환·기존 입력·설정 복원·소유권별 비활성화가 유지되는지 확인한다. 대상은 `UDemonicUITheme`·`UDemonicComboBoxString`과 메뉴·설정/15초 확인·캐릭터 생성/직업 상세·개발용 협동·RunMap·상점 선택/상점·결과·라운드 계획, GameplayRoot의 저장 복구/재시도·협동 상태/나가기 안내다. 적용 기준과 에셋 참조 구조는 [UI_README 9절](UI_README.md#9-demonicui-공통-테마)을 따른다.

### 15-2 준비 조건

1. 최신 소스의 프로젝트 파일 재생성과 Development Editor / Win64 빌드가 완료된 상태에서 UE를 재시작한다. 명령은 [README](../README.md#개발-환경)를 따른다. WBP·JSON·맵·Config 재생성은 필요하지 않다.
2. `/Game/User_JeHoon/LEVEL/MainMenu`와 원본 `/Game/DemonicUI` 콘텐츠를 유지한다. 일반 Run용 저장 보존은 보고서 상단의 준비 조건을 따른다.
3. 화면 전환·해상도 시험은 [14-2 준비 조건](#14-2-준비-조건)의 독립 게임 창을 사용한다. 현재 해상도·화면 모드·OS 배율과 설정 저장값을 기록한다.
4. 협동 비교는 [9절](#9-개발용-협동-ui)의 2개 독립 창과 Host/Client를 준비한다. 패키지 확인은 사용자가 최신 코드로 만든 별도 패키지에서 수행하며 Editor 성공으로 대체하지 않는다.
5. MainMenu의 관리 이어가기 안내는 기존 C++ 개발 fixture에서 호출자·저장 대상을 명시적으로 연결한 경우에만 표시된다. 해당 준비가 없으면 안내 동시 표시 조건은 대기로 남긴다.
6. 지도·결과는 기존 `WBP_RunMapWidget`·`WBP_EncounterResultWidget`이 연결된 경로를 확인한다. 저장 복구/재시도 안내는 기존 표시 조건이 제공되는 경우에 확인하며 조건을 준비하지 못한 세부 항목은 미실행으로 남긴다.

### 16-4 개발 확인과 제한

Development Editor / Win64 컴파일이 성공했으며 컴파일 오류·경고는 0이다(14.79초, `Saved/Logs/UnifiedDPIBuild.log`). UI 소스와 JSON 명세에서 개별 `ScaleBox`·`SetRenderScale`·`SetStretch`·수동 DPI 보정 잔존 0개, 카메라 설정과 생성 스크립트의 Python 문법을 정적으로 확인했다.

공식 엔진 수식으로 8개 뷰포트의 배율을 확인했다. 1280×720은 0.666667, 1920×1080은 1, 2560×1440은 1.333333, 3840×2160은 2, 2560×1080은 1, 3440×1440은 1.333333, 1600×1200은 0.833333, 800×600은 0.416667이다. 배율을 적용하기 전의 논리 UI 영역은 모두 1920×1080 이상이었다. 이 결과는 정적 계산이며 실제 화면 렌더링·입력 검증은 아니다.

변경 문서의 로컬 링크·앵커·코드 블록·16절 검증 ID 8개의 유일성/미실행 표기와 `git diff --check`를 검사했다. 기존 DemonicUI의 컴파일·에셋 조사 기록은 이번 공통 배율·카메라 변경의 성공 근거로 사용하지 않는다.

PIE·게임 플레이·Unreal 자동화 테스트·패키지 실행은 수행하지 않았다. 실제 화면 비율·가독성·시야·입력 결과와 런타임 오류·경고는 미확인이다. 위 항목과 [14절](#14-시작-메뉴-화면그래픽-설정)의 설정 계약을 사용자가 확인하며 결과 전에는 완료로 변경하지 않는다.

### 18-1 목적과 대상

전투 준비 취소 중 저장 실패로 진행이 멈추는 문제를 복구하고, 파티 설정 오류를 게임 시작 전에 찾는다.

- `AEncounterManager`는 준비 오류와 취소 대기를 보존한다. 기존 재시도 경로에서 취소를 우선 처리하며, 저장과 동기 Map 이벤트 동안 새 전투·재시도 진입을 차단한다. 마지막 화면 통지 전에 가드를 해제해 재시도 버튼을 갱신한다.
- `URunStateSubsystem::AbortEncounter`는 일반·관리 Run 모두 저장 실패 시 원래 단계·노드를 복구한다. 기존 확정 저장은 유지하며 저장 성공 시에만 Map을 공개한다.
- 로컬·복제 표시 데이터 모두 준비 실패 원인과 저장 오류를 중복 없이 함께 표시한다. 취소 저장 성공 후 Map에는 준비 오류를 유지한다. 재시도는 현재 로컬 Host만 수행한다.
- `AGameplayPlayerController`의 화면 갱신은 Run의 Combat 단계와 실제 전투 활성 여부를 모두 확인한다. 준비 취소 저장 실패·중단·종료 상태에서 입력을 다시 활성화하지 않는다.
- 파티 Data Validation은 런타임 직업 해석을 공유한다. 클래스 fallback과 클래스 기본값 사용을 유지하며 직업 ID·문제 필드·에셋 경로를 오류에 포함한다. 새 밸런스·아이템 규칙은 추가하지 않는다.
- 결과 화면의 Continue 저장 재시도가 성공하면 동기 상태 통지 전에 이전 오류를 지운다. 실패 시 Result와 확정 저장을 보존하고 새 저장 오류를 표시한다.
- 실제 해석된 직업 클래스가 `Abstract`·`Deprecated`이면 사전 검사와 런타임 해석에서 거절한다. 명시 클래스 → 기존 매핑 → 공통 fallback 우선순위는 유지하며 잘못된 상위 클래스를 조용히 fallback으로 대체하지 않는다.

## 19 서버 공격 충돌 판정

### 19-1 목적과 대상

공격 선택만으로 피해가 보장되지 않고 실제 서버 충돌로 적중하는지 확인한다. 기준은 [GAME_DESIGN 8-5](GAME_DESIGN.md#8-5-발동과-피격)이며 대상은 `CombatRoundCoordinator`, `CombatRoundProjectile`, `FCombatRoundSkill`과 기존 `CombatRoundTests.cpp`다.

- 근접은 시전 완료 시 전방 구체 스윕과 가장 먼저 충돌한 적 캡슐 1개에 피해를 적용한다. `HitRange`는 전방 끝 거리, `MeleeRadius`는 판정 폭·높이의 반경이며 기본값은 35cm, 실제 반경은 사거리 절반 이하로 제한한다.
- 지점 공격은 지정 중심의 `HitRange` 반경 구체와 겹친 적 캡슐에 각각 1회 적용한다. 중심부터 실제 캡슐 최단 접점까지 장애물이 있으면 해당 적은 피해를 받지 않는다.
- 투사체는 초기 겹침·이동 스윕에서 첫 유효 적 또는 장애물에 닿으면 종료한다. 현재 전투의 적만 허용하며 별도 전투 유닛은 흡수하지 않는다. 명시적인 투사체 `bTargetOnly` 프로필은 유지한다.
- 세 공격 모두 살아 있는 적의 실제 캡슐만 사용한다. 아군·사망 유닛·장식 메시·센서는 피격되지 않는다. 장애물은 `WorldStatic`·`WorldDynamic` 객체 중 `WorldDynamic` 응답이 `Block`인 물체이며 Visibility 전용 그리드와 Overlap 센서는 차단하지 않는다.
- 기존 `WindupSeconds`와 서버 시간차 실행을 사용한다. 무기 메시·애니메이션 알림 기반 타격 구간, 명중 확률, 성공 슬롯, 치명타·상태 발동 조건의 신규 구현은 포함하지 않는다.

## 21 DA 시전 몽타주 연결

### 21-1 문제와 대상 변경

사용자가 전투 검수 중 DA의 애니메이션이 적용되지 않는다고 보고했다. 기존 `BPDA_DefaulatAttack` → `BPGA_DefaultAttack` → `MM_Attack_01_Montage`와 범위 공격의 `MM_Attack_03_Montage` 연결은 존재했지만, 라운드 스킬 해석은 공격 Ability의 피해 수치만 가져오고 몽타주 재생 경로를 연결하지 않았다.

- `bUseRoundDefinition`을 켠 명시 프로필은 선택적 `RoundDefinition.CastMontage`를 우선 사용한다. 미지정 명시 프로필과 기존 자동 변환은 공격 Ability의 `GetAuthoredAttackMontage`를 사용한다.
- Casting 진입 시 시전 몽타주를 한 번 재생한다. 서버 multicast는 표현을 전달하며 재생 시작 실패는 `[RoundAnimation]` 경고로 유닛·몽타주·AnimInstance를 기록한다.
- 서버 `WindupSeconds`·충돌·AP와 발동 1회는 유지한다. 후속 복귀 보완은 실제 서버 몽타주 인스턴스가 블렌드 아웃까지 끝난 뒤 복귀하도록 하며, 재생 불가·반복·종료 누락의 제한 대기는 [21-5](#21-5-전체-시전-대기와-da-폴더-정리)를 따른다. 사망·중단·발동 전 취소·다음 행동에서는 해당 재생 인스턴스를 정리한다.

### 21-5 전체 시전 대기와 DA 폴더 정리

목적: 공격 몽타주가 끝나기 전에 복귀 이동이 시작되는 문제를 보완하고 제작 DA를 유형별로 정리한다. 기본 공격 외의 공격은 미작성 상태가 맞다는 사용자 확인을 반영하며 스킬 수치·능력·몽타주를 새로 작성하지 않는다. 사용자가 저장한 이름·ID와 기존 에셋 이름 `BPDA_DefaulatAttack`도 유지한다.

대상 변경:

- 피해·투사체 발사와 AP 처리는 기존 `WindupSeconds`·서버 충돌 판정으로 한 번 실행한다. 발동 뒤 `Recovery`는 해당 서버 몽타주 인스턴스 ID를 추적하여 블렌드 아웃까지 끝난 뒤 복귀로 전환한다. 기다리는 동안 이동 속도는 0이며 애니메이션 알림이 추가 공격을 실행하지 않는다.
- 서버 재생 인스턴스를 사용할 수 없으면 에셋 길이/RateScale·블렌드 아웃·0.25초 여유 시간을 기준으로 기다린다. 시전 시작 기준 최대 60초의 대기 제한을 두고 반복 섹션·자동 종료 누락·잘못된 길이/속도를 경고한다. 제한 도달 시 남은 표현을 즉시 정리하여 무한 대기를 막는다. 정상 몽타주의 자연 종료와 제한에 의한 종료는 구분해 확인한다.
- 대기 시간은 실제 서버 프레임의 `DeltaSeconds`를 한 번 누적한다. 고정 간격 시뮬레이션의 미처리 시간과 분리하여 프레임 지연 뒤 누적 시뮬레이션 처리로 복귀 대기가 조기에 끝나지 않게 한다.
- 사망·중단·발동 전 취소의 정리를 유지한다. 정상 복귀가 끝나면 시작 방향과 정지 속도를 복원하며 성공한 잔류 이동의 조준 방향은 유지한다.

### 22-1 변경 범위와 준비

2026-09-16 사용자 요청으로 선택 직업을 전사 `Warrior`·마법사 `Mage`·궁수 `Archer`·도적 `Rogue`로 통일했다. `UProfessionBase`와 네 native 자식 클래스가 공통 시작 HP 100·힘/민첩/지능 각 10을 제공한다. Party의 `ProfessionClass`를 연결하고 기본값 사용 시 HP/세 능력치는 직업 정의, AP/SubAP/시작 스킬은 기존 전투 클래스에서 읽는다. 직업별 최종 밸런스·성장 공식·추가 공격은 작성하지 않는다.

### 23-1 대상 변경과 범위

게임 시작은 새 native `UGameModeSelectionWidget`을 연다. 싱글플레이는 기존 CharacterCreation으로, 멀티플레이는 기존 같은 PC·LAN의 2~4인 개발용 방으로 연결한다. 첫 화면의 별도 개발용 협동 버튼은 제거했다. 기존 Listen Server·궁수 1명 배정·Host 진행 권한·Shipping 비활성·Steam 미지원 범위는 유지한다. 모드 선택에서 뒤로가기는 첫 화면, 캐릭터 생성·접속 시작 전 멀티 화면의 뒤로가기는 모드 선택으로 돌아간다. 멀티 접속 이후 취소/나가기는 기존 세션 정리·메뉴 복귀를 따른다.

이어하기 옆 104×40 항복 버튼은 현재 유효한 일반 싱글 Continue 대상이 있을 때만 활성화한다. `URunSurrenderWidget` 확인창은 돌아가기를 기본 포커스로 사용하고 아래 메뉴 클릭·중복 제출을 막는다. 취소는 무변경이며 확인 시 권한·현재 파일을 다시 검사한다. 확인 당시와 슬롯/내용이 다르면 거절하고, 삭제 실패는 파일과 현재 Run을 유지한다. 성공한 경우에만 해당 저장 슬롯·현재 Run을 정리하고 이어하기/항복을 비활성화한다.

저장 포기 방식은 별도 사용자 선택 응답 없이 기존 자율 진행 위임에 따라 적용한 기본안이다. 협동·관리·계정 제공자 저장의 항복이나 랭크 결과·패배 기록 보존 정책은 추가하지 않았다. 종료된 저장·손상 파일·구직업·이전 Combat처럼 일반 Continue가 거절하는 데이터도 이 버튼으로 삭제하지 않는다.

### 23-3 개발 확인과 제한

Development Editor / Win64 빌드와 UHT를 통과했다. 최초 빌드의 상속 멤버명과 지역 변수명 충돌 및 Windows 삭제 정보 초기화 오류를 수정한 뒤 5.64초 빌드에 성공했다. 삭제 공유 reader가 남는 경우의 삭제 대기 문제를 독점 핸들로 보완하고 회귀를 추가한 최종 빌드는 4.90초·컴파일 오류/경고 0이다(`Saved/Logs/MenuModeBuildVerified.log`). 회귀 코드도 컴파일했으며 실행하지 않았다.

문서 10개·로컬 링크 313개·앵커 219개·표 111개, JSON과 Python 구문·프로젝트 파일 항목을 검사했다. 사용자 `.sav` 26개의 SHA256과 파일 목록이 작업 전후 동일하다(`Saved/Automation/MenuModesStatic.json`). 실제 항복으로 저장을 삭제하지 않았다.

## 24 민첩 기반 전투 속도와 일반 적 능력치

### 24-1 변경 범위

사용자 요청으로 민첩 1당 전투 속도 1을 적용하고 일반 테스트 적의 힘·민첩·지능을 각각 5로 설정한다. `AUnitBase::GetCombatSpeed()`는 현재 GAS `Dexterity`를 float로 읽으며 독립 속도 20을 제거한다. 기본 아군의 세 능력치는 기존 10·속도 10, 일반 `AEnemyUnit`은 세 능력치 5·속도 5다. 일반 적 HP 150·AP 2와 기존 스킬은 유지한다. Snapshot 적은 저장된 능력치로 덮어쓰므로 저장된 민첩이 실제 속도가 된다.

서버는 각 라운드 Planning 진입 시 양 진영 생존자의 속도와 `(최고 속도 − 해당 속도) × 0.1초` 지연을 고정한다. 기본 구성에서 아군은 0초, 일반 적은 0.5초 후 행동을 시작한다. 실제 타격 시점은 접근·시전에 따라 달라진다. 라운드 중 민첩 변경·사망으로 현재 시각표를 다시 만들지 않고 다음 Planning에서 새 민첩을 읽는다. 이동·시전·투사체 속도나 피해·명중 공식을 추가하지 않는다.

복제용 라운드 View의 Speed도 float를 사용한다. 계획 화면의 속도/지연과 직업 상세의 민첩은 `FText::AsNumber`로 표시하며 직업 상세에 민첩과 같은 속도를 별도로 표시한다. 기본 표시의 소수 자릿수는 최대 3자리이며 내부 계산은 표시용 반올림과 구분한다. 별도 Snapshot 속도 필드를 추가하지 않는다.

### 24-3 개발 확인과 제한

Development Editor / Win64 전체 빌드는 UHT와 변경 회귀 소스를 포함해 21.62초에 성공했다. UHT 생성 파일 8개·빌드 작업 24개, 컴파일 오류/경고 0이며 Live Coding 검증이 아니다(`Saved/Logs/DexteritySpeedBuild.log`). `Build.bat ProjectAEditor Win64 Development -WaitMutex -FromMsBuild -architecture=x64 -NoUBA -NoHotReloadFromIDE`와 현재 `.uproject` 경로를 사용했다.

읽기 전용 commandlet에서 네이티브 Unit/Enemy와 기존 `BP_PlayerUnit`·`BP_EnemyUnit`·`BP_SnapshotOpponent`의 클래스 기본값 5개를 확인했다. 기본 아군의 세 능력치/속도 10, 일반 적 계열 기본값 5와 네 직업 HP 100·세 능력치 10을 확인했다. 초기 검사 스크립트의 비Blueprint 대상·Python 미노출 메서드 호출을 수정한 최종 검사는 오류/경고 0으로 종료했다(`Saved/Logs/VerifyDexteritySpeedDefaultsComplete.log`, `Saved/Automation/DexteritySpeedDefaults.json`). Actor 생성·플레이·에셋 저장을 실행하지 않았으며 Snapshot 런타임 덮어쓰기 성공을 이 검사로 판정하지 않는다.

`ProjectA.Combat.Round.DexteritySchedulesRoundActions`를 추가하고 `ProjectA.Party.ProfessionLoadout`을 보강했다. 기존 라운드 fixture의 직접 속도 설정을 GAS 민첩 설정으로 바꾸고 기본 직업 10·일반 적 5·Snapshot 설정 13/17/19와 속도 17을 검사하도록 작성했다. 새 라운드 회귀는 기본 시작 지연, 소수 민첩 21.25, 라운드 중 시각표 고정과 다음 Planning 반영을 다룬다. 관련 회귀는 컴파일했고 실행하지 않았다. Snapshot 소수 민첩 저장/복구는 기존 `ProjectA.Snapshot.SaveGameRoundTrip`과 연결한다.

최종 정적 검사는 문서 10개·로컬 링크 319개·앵커 225개·표 112개, 읽기 전용 Python 구문과 변경 C++ 11개의 기존 `.vcxproj`·`.filters` 항목을 통과했다. 사용자 `.sav` 26개의 파일 목록과 SHA256은 작업 전후 동일하다(`Saved/Automation/DexteritySpeedStatic.json`). 독립 코드 검토와 `git diff --check`도 통과했다.

C++ 파일 생성·삭제·이름 변경이 없어 Visual Studio 프로젝트 재생성은 필요하지 않다. Visual Studio와 에디터 창은 열지 않았다. Config·콘텐츠 에셋 변경은 없으며 `AGENTS.md`에 사용자 요청 없는 작업 종료 시 에디터 자동 실행 금지를 반영했다.

PIE·게임 플레이·Unreal 자동화·2인/4인 검증은 미실행이다. 작업 완료 후 사용자 요청 없이 에디터 창을 자동 실행하지 않는다.

## 25 싱글플레이 직접 조작 캐릭터 선택

### 25-1 변경 범위와 저장 호환

사용자의 명시적 선택에 따라 일반 싱글 새 게임에서 직접 조작할 캐릭터 한 명을 캐릭터 생성 화면에서 고른다. 생성 카드의 Edit/X 행에 `직접 조작` 버튼을 추가하고 선택한 카드는 `선택됨`, 직업명 옆은 `직접 조작`으로 표시한다. 다른 생성 동료는 `AI`로 표시한다. 선택 전에는 시작을 막으며 선택 카드 삭제 시 다시 선택해야 한다. 직업·이름 편집은 선택을 보존하고 화면 재진입은 초안·선택을 초기화한다.

선택은 `FRunPartyMember::bPlayerControlled`로 저장하며 기존 저장 버전은 유지한다. 일반 `LocalDevelopment`의 원래 참가자가 한 명일 때만 선택 슬롯을 `Human`, 나머지를 `ServerAI`로 설정한다. 선택과 `CharacterId`·`SlotIndex`·원래 소유권은 함께 유지한다. 인간 캐릭터가 사망하면 생존 AI는 준비 입력 없이 전투를 계속한다. 다음 전투에서 HP 0인 선택 캐릭터가 스폰하지 않아도 생존 동료의 AI 상태를 유지하며 인간 조작을 승계하지 않는다.

| 데이터 종류 | 적용 규칙 |
|---|---|
| 새 일반 싱글 파티 | UI에서 생성한 한 명을 명시 선택해야 시작. 선택을 다음 저장·이어하기·전투에 유지 |
| 명시 선택이 있는 일반 단일 참가자 저장 | 선택을 그대로 복원. 복수 선택·미생성 슬롯 선택은 거절 |
| 선택 필드가 없거나 모두 false인 이전 일반 단일 참가자 데이터 | 생성 멤버의 가장 낮은 SlotIndex를 메모리에서 선택. HP 0도 제외하지 않으며 다음 정상 저장에 선택 보존 |
| LegacyOffline | 선택 정규화·AI 전환 없이 기존 전체 인간 조작 유지 |
| 협동·관리 Run·관리 싱글 전환 | 기존 소유 계정·HumanParticipants 규칙 유지. 싱글 선택 필드가 권한을 대체하지 않음 |

기존 구직업·이전 Combat 저장 거절은 유지한다. 호환 처리 때문에 사용자 저장을 일괄 변환하거나 삭제하지 않는다. 전투 중 체크포인트 복구나 동료 수동 전환 기능은 추가하지 않는다.

### 25-3 개발 확인과 제한

구현 대상은 `UCharacterCreationWidget`의 선택 UI, `FRunPartyMember`와 `URunParticipationLibrary`의 선택 해석, `URunStateSubsystem`의 저장/복원, `AEncounterManager`의 매 전투 조작 모드 설정이다. 원래 소유권과 기존 AI 계획·준비·승패 처리를 사용한다. 기존 Designer/native 공용 슬롯 행에 버튼을 추가하므로 콘텐츠 에셋·생성 명세 재생성은 필요하지 않다.

새 회귀 `ProjectA.Run.Encounter.StandaloneControlSelectionPersists`는 후순위 선택·잘못된 선택·HP 0 선택 고정·SaveGame/StandaloneContinue·상점 이후 Combat_02 진행·이전 무선택 데이터 정규화를 다룬다. `ProjectA.Combat.Round.StandaloneCompanionsKeepAIControl`은 동일 소유자 파티의 선택 캐릭터 입력 권한·AI 명령 거절·인간 사망 후 AI 진행과 다음 전투의 선택 캐릭터 미스폰 상태를 다룬다. 관리/협동 선택 비트의 비간섭은 기존 `ProjectA.Recovery.ParticipationValidation`을 보강한다.

기존 `ProjectA.VerticalSlice.SavedMenuLifecycle`은 native/Designer 경로의 선택·삭제·화면 재진입·상세 패널 가드를 보강했다. 위 회귀의 다음 전투 검사는 Run 단계·저장 재로드와 별도 native 라운드 fixture로 나뉘며 전체 Encounter Blueprint 스폰을 실행한 결과가 아니다. 회귀 소스 작성·컴파일과 실제 실행을 구분한다.

Development Editor / Win64 빌드는 변경 회귀 소스와 UHT를 포함해 18.32초에 성공했다. UHT 1.249초·생성 파일 13개·빌드 작업 23개이며 컴파일 오류/경고 0이다(`Saved/Logs/StandaloneControlBuild.log`). `Build.bat ProjectAEditor Win64 Development -WaitMutex -FromMsBuild -architecture=x64 -NoUBA -NoHotReloadFromIDE`와 현재 프로젝트 경로를 사용했다. 이전 24절 결과와 구분하며 Live Coding 검증이 아니다.

UI·백엔드·회귀의 독립 정적 검토에서 추가 결함을 발견하지 않았다. 최종 정적 검사는 문서 10개·로컬 링크 329개·앵커 235개·표 114개, 변경 C++ 11개의 기존 `.vcxproj`·`.filters` 항목 각 1개와 Designer 선택 버튼의 부모 행 4개 명세를 확인했다. 프로젝트 항목 검사의 초기 부분 문자열 중복 경고는 정확한 경로 비교로 해소했으며 실제 누락은 없었다. 빌드 전후 사용자 `.sav` 26개의 파일 목록과 SHA256이 동일하다(`Saved/Automation/StandaloneControlStatic.json`).

C++ 파일 추가·삭제·이름 변경과 콘텐츠 에셋 변경이 없어 프로젝트/WBP 재생성이 필요하지 않다. Visual Studio는 실행하지 않았다. 작업 중 발견한 기존 에디터는 정상 종료했으며 강제 종료·재실행은 하지 않았다.

PIE·게임 플레이·Unreal 자동화·에디터 에셋 검사·2인/4인 검증은 모두 미실행이며 사용자 확인을 기다린다. 사용자 요청 없이 작업 완료 후 에디터 창을 자동 실행하지 않는다.
