# T14 협동 플레이와 중단 후 이어하기 설계

정리일: 2026-09-10

[T14 작업 카드](TODO.md) · [게임 기획 방향](GAME_DESIGN.md) · [프로젝트 기획과 구현 현황](PROJECT_PLAN.md) · [프로젝트 안내](../README.md)

이 문서는 사용자 확정안을 기록하고 후속 구현의 경계를 정한다. 순차 1~5번과 7번의 독립적인 실제 2·3·4인 전투·끊김·기존 Host 복구를 검증했다. 후속 답변으로 합류 번호순 승계, 사전 동의 없는 Host 단독 AI 전환, 해당 Run의 AI 유지, Steam 우선과 Host의 노드·Continue 결정권을 확정했다. 아래 규칙은 이전 사전 동의·복귀·결정권 대기 내용을 대체한다. 6번의 관리 v4·싱글 전환 메뉴·영속 참여 목록·승계 복구를 로컬 개발 저장소에 연결하고 실제 관리 PIE 2건·전체 회귀 75건을 통과했다. 6번은 로컬 개발 범위 완료이며 7번의 원래 4인→현재 3인 승계 확장을 이어간다. 8번의 실제 Steam/PlayFab 서비스·MMR은 미구현이다. 현재 결과와 실행 경계는 [Listen Server 안내](T14_NETWORK.md), [확정 턴 저장·복구](T14_CHECKPOINT.md), [명시적 재개 안내](T14_RESUME.md), [순차 대기열](T14_QUEUE.md)을 따른다.

## 1. 확정한 플레이 규칙

| 항목 | 확정 내용 |
|---|---|
| 협동 인원 | 최대 4명. 첫 네트워크 검증은 Listen Server와 Client 2명으로 시작한다 |
| 인간 조작권 | 각 플레이어는 자신의 캐릭터만 직접 조작한다. Host도 다른 사람의 캐릭터를 직접 조작할 수 없다 |
| 캐릭터 소유권 | 원래 소유자를 유지한다. Host 변경이나 AI 조작 전환은 캐릭터 소유권 이전이 아니다 |
| 참가자 | 원래 Run 참가자 외 다른 사람의 대체 참가를 허용하지 않는다 |
| 종료·연결 끊김 | 정상 종료나 갑작스러운 끊김만으로 Host를 바꾸지 않는다. 기록상 기존 Host를 유지한다 |
| 최초 참가 번호 | 최초 Host는 1번, 최초 합류 순서대로 2·3·4번. 재접속이나 캐릭터 배치 변경으로 다시 번호를 매기지 않는다 |
| 중단 후 이어하기 | 명시적으로 재개할 인간 원래 참가자 중 가장 작은 번호가 Host를 승계한다. 2·3·4번이 혼자 싱글로 전환하면 본인이 Host가 되고 나머지는 AI가 된다 |
| AI 전환 결정 | Host가 단독 확정한다. Run 시작 시 개인별 사전 동의는 요구하지 않는다 |
| AI 전환 후 복귀 | 해당 Run 종료까지 AI를 유지한다(3C). 원래 소유자가 돌아와도 인간 조작이나 Host를 자동 반환하지 않는다 |
| 전투 밖 진행 | 다음 노드 선택과 승리 후 Continue는 현재 Host만 확정한다(5A) |
| 온라인 연결 | Steam P2P 우선. Steam+PlayFab(4B)의 무료 개발 범위와 운영비 조건은 별도 확인한다 |
| 경쟁 목표 | MMR·랭크를 도입한다. AI 전환 후에는 현재 인간 참여자만 MMR에 반영하고, 불참자에게 추가 변동을 적용하지 않는다 |
| 복구 시점 | 마지막 확정 턴 경계에서 복구한다. 처리 중인 행동·턴을 임의로 완료한 것으로 간주하지 않는다 |

최대 4명은 목표 접속 인원이다. 한 사람이 여러 자기 캐릭터를 가질 수 있는지, 반드시 1인 1캐릭터인지, 배정할 캐릭터보다 접속자가 많을 때의 처리는 미정이다. 자동 균등 배정으로 소유권을 다시 나누는 규칙은 도입하지 않는다.

## 2. Host 유지와 승계의 의미

Host가 게임을 종료하면 그 컴퓨터의 Listen Server도 더 이상 실행되지 않을 수 있다. **기존 Host 유지**는 Run 기록의 Host 자격을 유지한다는 뜻이며, 오프라인 컴퓨터에서 서버가 계속 실행된다는 뜻이 아니다.

다음 세 상황을 구분한다.

1. **일시적인 끊김:** 원래 소유자와 Host 기록을 유지한다. 끊김 자체를 AI 전환 동의 실행이나 Host 승계로 처리하지 않는다.
2. **기존 멤버의 재집결:** 기존 Host와 확정 체크포인트를 기준으로 재개하는 경로다.
3. **명시적인 AI 이어하기:** 원래 멤버의 재집결이 어려울 때 기존 참가자가 이어하기를 선택한다. 이번에 인간으로 재개할 원래 참가자 중 가장 작은 최초 번호를 Host로 정하고, 이 Host가 불참 AI 전환을 확정한다. 싱글로 전환하기에서는 선택한 본인만 인간으로 남는다. 개인별 사전 동의는 검사하지 않으며 최신 체크포인트·기존 실행 권한·원래 참가자·이미 AI인 참가자의 복귀 금지는 검증한다.

세 번째 경로는 진행 중인 서버 연결을 즉시 옮기는 자동 실시간 Host Migration과 다르다. 중단된 Run의 확정 데이터로 새 세션을 열어 재개하는 기능이다.

새 Host는 서버를 실행하고 서버 AI를 진행할 수 있지만, 다른 사람의 캐릭터를 인간 입력으로 조작할 수 없다. 예를 들어 2·4번이 함께 재개하면 2번, 4번만 재개하면 4번이 Host다. 이미 AI로 전환된 참가자는 그 Run의 인간 재개 후보에 다시 넣지 않는다. 다른 Host가 실행 중인 Run을 로컬 파일 복사나 버튼 클릭만으로 빼앗는 규칙은 아니다.

## 3. AI 전환과 MMR 경계

사용자는 후속 확인에서 사전 동의를 없애고 Host가 단독 결정한다고 명시했다. 기존 저장의 `AIConsent`와 `ConsentPolicyVersion`은 구버전 자료의 구조 호환을 위해 읽되 AI 준비·실행·복구의 승인 조건으로 사용하지 않는다. Host의 결정은 서버 AI에게 조작을 넘기는 범위이며 타인이 직접 조작하거나 장비·스킬을 자유롭게 편집하는 권한으로 확대하지 않는다.

전투 시작 전 신뢰된 서버 C++ 모드 설정과 저장 복원은 원래 소유권·파티 유형·서버 권위를 유지한다. 기존 동의가 `Unknown`·`Declined`여도 AI를 허용한다. 6번의 관리 v4는 Human 목록을 전투 밖에도 저장하고 재개 시 이전 목록의 부분집합만 허용하여 3C를 적용한다. 메뉴 버튼은 본인 한 명의 Human 목록으로 최신 기록을 획득한 뒤 새 Gameplay를 연다. 원래 참가자 전원 연결을 요구하는 일반 v3 경로와 현재 Human만 요구하는 관리 v4 경로를 구분하며, 새 관리 경로의 실제 세션 검증 결과는 별도로 기록한다.

AI 이어하기가 확정된 뒤에는 현재 인간 참여자에게만 MMR을 반영하고 불참자에게 추가 MMR 변동을 적용하지 않는다. 불리한 결과 직전 이탈하는 악용 가능성은 후속 정책으로 해결한다. 임의 이탈 패널티, 불참자 점수 차감, 전체 원래 참가자에게 결과를 반영하는 규칙을 추가하지 않는다.

다음 세부 정책은 미정이다.

- 비전투 중 AI 캐릭터의 장비·스킬·보상 선택을 누가 결정할지
- MMR의 현재 인간 참여자를 판정하는 기준 시점과 이탈·재접속 악용 방지 방법
- 일시적인 Client 끊김 동안 턴 대기·일시정지·시간 제한을 어떻게 처리할지
- 돌아온 AI 소유자에게 관전 접속을 제공할지. 인간 조작 복귀는 해당 Run에서 허용하지 않는다
- 중앙 저장·결과 검증의 무료 개발 한도와 출시 운영비. P2P가 이 책임을 대체하지 않는다

## 4. 필수 데이터 경계와 설계 후보

1번 작업으로 `FRunIdentityData`·`FRunAccountId`·`FRunParticipantData`, `FRunPartyMember.CharacterId/OwnerAccountId`, 참가자·소유권 조회를 추가했다. 일반 Run의 전투 밖 저장은 v2, 4번의 확정 턴 저장은 v3다. 기존 식별 정보 없는 v1은 `LegacyOffline`으로 읽고 v1으로 다시 저장하며 소유권을 추정해 이관하지 않는다. `PartySnapshot`은 v1을 유지한다. v3는 로컬 revision·AttemptId·턴 순서·유닛/장착/고정 Snapshot 본문을 저장한다. 5번에서 이 전투 본문의 schema 2에 파티 Human/ServerAI 모드를 추가했다. schema 1은 Human만 허용하며 기본 빈 체크포인트의 schema 1을 유지해 기존 Run v1/v2와 호환한다. 실행 중 AI 세션 식별자는 저장하지 않고 새 세션에서 다시 생성한다.

6번의 관리 Run v4는 Identity schema 2·원래 참가자 2~4명의 명시적 번호와 영속 `FRunParticipationData`를 요구한다. 새 Host·HostEpoch·Human 목록과 전투 Identity/모드를 하나의 본문으로 확정하며 원래 캐릭터 소유자와 AttemptId·확정 턴을 보존한다. 관리 기록은 로컬 기준 저장소의 revision·실행 SessionId·lease로 보호하며 일반 v1~3 저장/이어하기와 분리한다. 구버전 전투 AI 플래그를 Human 이력으로 추정 이관하지 않는다. 원격 중앙 저장과 MMR 판정 이력·결과 반영은 후속 범위다. 구현 상태는 [순차 작업 대기열](T14_QUEUE.md)을 따른다.

| 데이터 경계 | 후보 정보 | 책임 |
|---|---|---|
| Run 식별과 원래 참가자 | `RunId`, 원래 참가자 계정 목록, `JoinOrdinal` | 같은 Run 식별, 대체 참가 거절, 최초 합류 순서 유지 |
| 캐릭터의 원래 소유자 | `CharacterId`, `CharacterOwnerAccountId` | 접속·Host 변경과 독립적으로 인간 조작권 검증 |
| 세션 Host | `HostAccountId`, `HostEpoch` | 현재 유효한 Host와 승계 세대 식별 |
| 참가·조작 상태 | Human/ServerAI 모드, 관리 v4의 영속 Human 목록·복원 대기 | 파티 소유권과 조작 주체 분리. 재개 시 기존 Human의 부분집합만 허용 |
| 이전 동의 기록 | 기존 `AIConsent`·정책 버전 | 구버전 구조 호환만 유지. 새 AI 전환 승인 조건으로 사용하지 않음 |
| 확정 체크포인트 | `Revision`, 확정 턴 식별자, 데이터 버전, 상태 본문 | 재개할 단일 상태 결정 |
| 전투와 결과 | `EncounterId`, `AttemptId`, 결과 식별자·반영 상태 | 결과 재전송과 중복 반영 방지 |
| 참여 이력 | 현재 Human 목록, 후속 MMR용 참여 시점·이탈 이력 | 현재 목록만으로 미정인 MMR 참여 판정까지 구현했다고 취급하지 않음 |

계정 식별자는 인증된 연결에서 확인한다. Client가 Action Request에 임의로 적은 계정 이름을 소유권 증명으로 사용하지 않는다. `PlayerController*`, `APlayerState*`, Actor의 메모리 주소, 일시적인 접속 순서는 장기 소유자 ID로 저장하지 않는다.

네트워크 Actor의 `Owner`와 게임 규칙상 캐릭터 소유자는 다른 개념이다. 연결 변경·AI 전환을 위해 실행 중 연결이 바뀌어도 `CharacterOwnerAccountId`는 유지한다. Actor 소유 연결은 Replication과 RPC 전달에 영향을 주므로 별도 책임으로 취급한다. [Unreal 공식 Actor Owner 설명](https://dev.epicgames.com/documentation/unreal-engine/actor-owner-and-owning-connection-in-unreal-engine)

## 5. Action Request와 서버 실행

Client는 이동·스킬·대상·턴 종료의 의도를 요청한다. 순차 2번의 `FCombatActionRequest`에는 Run·Host 세대·전투 실행 ID·연결 바인딩 ID·턴 번호·요청 순번·행동 유닛 ID·스킬 PrimaryAssetId·대상 유닛 ID와 Grid 좌표를 담는다. Actor reference는 서버 실행 중 해석에만 사용하며 계정이나 비용을 요청 본문에서 받지 않는다. 회복약도 이 경로를 거친다.

`UCombatActionAuthority`는 CombatManager의 서버 객체로 Run/파티 값과 실행 중 유닛 매핑을 보관한다. 신뢰된 서버 코드가 Controller에 원래 참가자를 바인딩하고, PlayerController Server Reliable RPC가 자신의 연결로 받은 명령을 전달한다. 새 연결은 별도 바인딩 ID를 받으며 같은 바인딩을 반복해도 순번을 초기화하지 않는다. 응답의 `Accepted`는 디스패치 승인이고 비동기 행동 성공과 구분한다. 일반 Standalone 자동 바인딩은 개발용 단일 참가자만 대상으로 한다. 관리 v4는 원래 인원이 여러 명이어도 현재 Human이 호출자 Host 한 명이고 lease가 유효하면 그 계정만 바인딩한다. 네트워크 경로는 GameMode의 `AssignRunParticipant`와 `ApplyCombatParticipantBindings`로 신뢰된 서버 C++ 연결에 배정하며 일반 v3는 원래 참가자 전원, 관리 v4는 현재 Human 전원의 연결을 요구한다. 이 배정은 실제 로그인 인증이 아니며 인증 공급자 연동은 8번이다.

관리 전투 권위는 설정한 관리 여부를 `Reset` 후에도 유지하며 현재 Run의 lease·전체 Identity·Host 호출자·SessionId를 확인한다. Human 명령은 복원 대기 중에도 거절하고, AI/연결 배정/모드 준비는 유효 lease와 영속 Human 목록에 맞는 경우만 허용한다. 정상 종료는 전투·콜백 정리 후 lease 해제 순서다. 직접 lease를 먼저 닫은 잘못된 호출도 남은 권위 객체의 요청이 일반 싱글 경로로 우회하지 못하게 한다.

서버는 다음을 확인한 뒤 기존 행동 API를 실행한다.

- 현재 Run·Host 세대와 일치하며 이미 처리한 요청이 아닌지
- 요청 연결이 원래 참가자이고 해당 캐릭터의 소유자인지
- 실제 현재 턴, 생존, 행동 중 여부, AP/SubAP, 스킬 보유, 타겟, Grid 규칙을 만족하는지

5번의 `UPartyAutoCombatComponent`는 매 프레임 Tick 없이 턴 시작과 행동 완료 통지에서 회복약·스킬·이동·턴 종료를 선택한다. Client를 가장하지 않고 `ExecuteServerAI`의 별도 AI 세션·요청 순번으로 서버의 공통 `ExecuteUnitAction` 검증 경로를 이용한다. AI 모드에서는 원래 소유자의 인간 요청도 거절하며, 인간 입력의 요청 순번을 먼저 기록해 거절된 패킷의 재실행을 막는다. 판단 콜백은 전투·턴·AI 세션이 바뀌면 실행하지 않는다. 모드 변경은 전투 시작 전으로 제한하며 중단 후 불참 AI 이어하기는 6번이다.

`CombatManager`·`TurnManager`·Grid 점유·유닛 상태·HP/AP·사망·전투 결과는 서버가 확정한다. Client UI는 요청 중 상태와 서버가 확정한 결과를 표시한다.

3번에서 서버 전용 TurnManager, CombatManager의 전투/소유권 복제 뷰, GAS HP/MaxHP RepNotify, 유닛 AP/SubAP·장착·이동·턴/행동/사망 상태, Grid 점유·영역·전열 보호와 HUD를 연결했다. GameState는 Phase·파티·노드·결과의 읽기 전용 표시 값을 전달하고 클라이언트 GameInstance의 RunState를 서버 Run으로 복원하지 않는다. 네트워크 결과 화면에서는 최종 유닛 상태를 유지하고 명시적인 Continue 또는 월드 종료에서 정리한다. 실제 두 월드의 전투/HUD 일치, 전체 자동화 42건과 별도 Snapshot PIE를 통과했다.

## 6. 확정 턴 경계 복구

목표 복구점은 **마지막으로 저장 완료까지 확인된 턴 경계**다. 메모리에서 턴이 끝났다는 사실과 복구 가능한 기록이 확정됐다는 사실을 구분한다.

턴 경계 데이터에는 다음 정보가 필요하다.

- Run 진행과 참가자·소유자·Host·AI 상태
- 전투 ID·상대 Snapshot 확정 본문 또는 변경 불가 참조/해시·버전, 현재 턴 순서·다음 행동 주체
- 모든 유닛의 HP/AP/SubAP, 사망, Grid 배치, 스킬·장비·상태 효과 등 실제 전투 상태
- 계속되는 턴 효과·쿨다운·필요한 난수 상태와 이미 반영한 결과

이동·발사체·GAS 콜백이 처리 중인 순간을 확정 경계로 저장하지 않는다. 4번의 확정 경계는 이전 유닛 `OnTurnEnd` 완료 → 다음 생존 유닛 선택 → 저장 완료 → 다음 `OnTurnStart` 순서다. 저장 실패 시 다음 턴을 멈추고 같은 후보를 재시도한다. 복원할 때 다음 유닛의 AP/SubAP 초기화는 한 번만 실행한다.

저장된 경계 이후 처리 중이던 턴의 부분 변경은 복구점에 포함되지 않을 수 있다. 이 되돌림을 행동 단위 복구와 혼동하지 않으며, 미확정 턴을 반복해 유리한 결과를 얻는 방식의 대응 정책은 별도로 확정한다. 상대 Snapshot 슬롯의 내용이 나중에 바뀌어도 복구할 전투의 상대 빌드는 바뀌지 않아야 한다.

4번의 `RunSaveGame` v3는 현재 콘텐츠의 턴 경계와 유닛·장착·고정 상대를 저장한다. 지원하지 않는 활성 GAS 능력·지속 효과·쿨다운·상태 태그는 거절하며 범용 상태 효과·게임플레이 난수 복구까지 구현한 것은 아니다. 일반 v3 협동 복구는 원래 참가자 전원과 기존 Host의 서버 연결 배정 후 새 세션에서 실행한다. 관리 v4의 명시적 재개는 먼저 새 Host와 현재 Human 목록을 기준 저장소에 확정하고 그 Human만 연결한다. 목록과 전투 모드가 다르면 스폰 전에 거절하며 복원 성공 후에만 Human 입력을 연다. 실패 시 lease·복원 대기를 유지하고 원인을 표시한다. 저장 실패·손상·복구 검증과 로컬 저장의 한계는 [확정 턴 저장·복구](T14_CHECKPOINT.md), [명시적 재개 안내](T14_RESUME.md)에 기록한다.

4번은 Editor 빌드·전체 52건(성공 35·경고 동반 성공 17·실패 0), 독립 프로세스 Writer/Reader·원본 상대 교체/삭제 후 복구·별도 Snapshot PIE를 통과했다. 5번의 schema 2는 이 경계에 조작 모드를 추가하며, 복구 시 AI 세션을 새로 만든 뒤 정상 턴 시작에서 AI 판단을 실행한다. 5번은 최종 Editor Build5·전체 회귀 56건(성공 36·경고 동반 성공 20·실패 0), 실제 AI `Coop2` 1건과 독립 프로세스 AI `RestartWrite`·`RestartRead` 각 1건, 별도 Snapshot PIE 회귀 1건을 통과했다. 초기 테스트 생존 전제 보정과 상세 결과는 [대기열](T14_QUEUE.md)에 기록한다.

## 7. 승계와 경쟁 결과의 단일 권위

Host가 가진 로컬 저장을 복사하는 것만으로 같은 Run의 승계를 승인하지 않는다. 원래 Host의 복귀, 여러 기존 참가자의 동시 승계, 과거 저장 재사용으로 같은 Run이 갈라질 수 있기 때문이다.

MMR·랭크 적용 전에는 중앙 권위 기록이 다음을 보장해야 한다.

1. 같은 `RunId`에서 유효한 Host 세대와 확정 `Revision`이 하나뿐이다.
2. 승계는 현재 세대·revision을 확인해 원자적으로 승인한다. 승인 후 이전 Host 세대의 갱신·결과를 거절한다.
3. 동일 전투 시도 결과를 재전송해도 결과와 MMR은 한 번만 반영된다.
4. 이전 저장이나 낮은 revision으로 확정 기록을 되돌리지 않는다.
5. 승인된 후임자가 최신 확정 체크포인트를 얻을 수 있다. Host 로컬 파일이 유일한 복구 사본이어서는 원래 Host 없이 이어갈 수 없다.

제품 방향은 Steam+PlayFab로 선택했지만, 위 목록은 게임플레이의 Listen Server 권위와 온라인 Run·랭크 기록의 권위를 나누는 요구사항이며 현재 서비스를 연동했다는 뜻은 아니다. Host가 보고한 결과만 신뢰해도 되는지, 재현 검증·서버 계산 등 어떤 검증을 적용할지는 후속 결정이다.

6번의 로컬 개발 저장소는 동일 PC의 공유 경로에서 배타적 OS lease와 최신 stamp를 대조하고 새 본문을 원자적으로 확정한다. Create/Resume 성공 후에만 RunState를 교체하고, 일반 저장·확정 턴·결과·Continue도 관리 lease로 기록한다. 실제 원격 중앙 저장·온라인 위변조 방지·중복 MMR 반영은 구현하지 않는다. 이탈 악용 방지 정책도 별도 확정 전에는 랭크 준비 완료로 취급하지 않는다.

관리 메뉴는 신뢰하는 C++ fixture가 변경 불가능한 `LocalDevelopment` 호출자와 재개 대상을 설정한 경우만 표시한다. 기존 일반 이어하기와 `싱글로 전환하기`/`싱글 진행 이어하기`를 분리하며 UI가 계정을 입력받거나 접속 순서로 계정을 추정하지 않는다. `AccountProvider`를 개발 관리 Run으로 승격하지 않으며 실제 로그인·다른 PC 간 공유·로비·초대는 8번에 남는다.

기존 엔진 기능과 공식 수명 주기를 우선 사용한다. 아래는 ProjectA 적용 후보이며 신규 클래스를 모두 즉시 추가하라는 의미는 아니다.

|---|---|

| `PlayerState` | 인증된 참가자에 대응하는 실행 중 정보, 소유 캐릭터 ID·접속/Ready 상태. 장기 소유권 기록은 별도 직렬화 데이터로 유지 |

Server RPC는 소유 연결을 고려해야 하며, 서버에 전달됐다는 사실만으로 캐릭터 조작 권한이 검증되는 것은 아니다. [Unreal 5.7 RPC](https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-procedure-calls-in-unreal-engine?application_version=5.7)

`USaveGame`과 `UGameplayStatics`로 필요한 데이터를 저장·불러오는 엔진 흐름을 재사용한다. 저장 본문을 월드와 다시 연결하는 책임은 ProjectA에 있다. [Unreal Saving and Loading](https://dev.epicgames.com/documentation/en-us/unreal-engine/saving-and-loading-your-game-in-unreal-engine)

## 10. 단계별 후속 작업과 수용 기준

### A. 소유권과 2인 서버 명령

- 원래 참가자·캐릭터 소유자·접속 정보를 분리하고 인증 공급자와 임시 개발 ID의 경계를 정한다.
- Listen Server/Client 2개의 PIE에서 각자 자기 캐릭터만 이동·스킬·턴 종료를 요청한다.
- Host를 포함한 타인의 인간 요청, 오래된 턴·중복 요청·잘못된 타겟을 서버가 거절한다.
- 두 화면에서 같은 턴·Grid 점유·HP/AP·사망·전투 결과를 확인하고 기존 싱글플레이 회귀 검증을 통과한다.

### B. 턴 경계 체크포인트와 기존 Host 복구

순차 4번에서 검증을 완료했다. 아래의 저장·기존 Host 복구와 이후 Host 승계 승인을 구분한다.

- 저장 경계와 버전·호환 규칙을 확정한 후 새 체크포인트 형식을 구현한다.
- 정상 종료와 갑작스러운 끊김 후 마지막 확정 턴 경계에서 복구한다.
- 이동·발사체·피해 처리 중 끊겨도 저장된 턴 경계에 확정된 피해·자원·사망·결과는 누락되거나 중복되지 않는다. 이후 미확정 턴은 선택한 복구 정책대로 처리한다.
- 저장 실패·손상·구버전·늦게 도착한 저장 완료 응답을 검증한다. 기존 v1 기록은 승인한 호환 정책에 따라 처리한다.

### C. 아군 AI 판단·행동과 모드 복구

순차 5번에서 구현·전체 회귀·실제 AI Co-op·독립 프로세스 AI 복구 검증을 완료했다.

- 전투 시작 전 원래 소유권·서버 준비 조건을 검증하고 소유권·Host·팀을 바꾸지 않은 채 서버 AI 모드를 적용한다. 개인 사전 동의는 요구하지 않는다.
- 서버 AI가 회복약·이동·스킬·턴 종료를 공통 행동 검증 경로로 요청하며 같은 유닛의 인간 입력을 거절한다.
- 오래된 전투·턴·AI 세션·중복 요청·늦은 완료 콜백이 행동을 다시 실행하지 않는다.
- schema 1 Human 호환과 schema 2 모드·원래 소유권 검증, 실제 저장/새 Actor 복구 및 네트워크 상태 일치를 확인한다.
- 이 단계의 일반 v3 복구는 원래 참가자 전원 연결 조건을 유지하고 연결 끊김을 자동 전환이나 Host 승계로 처리하지 않는다. 6번 관리 v4의 영속 Human 예외와 구분한다.

### D. 명시적인 Host 승계와 불참 AI 이어하기

현재 순차 6번의 로컬 관리 v4·메뉴·Gameplay 경로를 연결하고 실제 세션 검증을 진행한다. 5번 전투 AI나 기존 7번 다인 복구 결과만으로 이 통합을 완료 처리하지 않는다.

- 최초 합류 번호와 현재 인간 참가 기록으로 Host 후보를 정하고 그 Host가 단독 확정한다. 대체 참가자와 AI로 전환된 사람의 인간 복귀는 거절한다.
- 승계 이후에도 캐릭터 소유권은 유지하고 새 Host의 타인 캐릭터 직접 조작을 거절한다.
- 원래 3명에서 2번 Host·3번 Client·1번 AI로 실제 새 Listen Server를 복구하고, 원래 4번은 실제 메뉴 버튼으로 본인만 Human인 Standalone을 연다. 실제 AI 행동·공유 상태와 결과/다음 전투의 영속 참여 목록을 검증한다.
- 실패 복원은 lease·대기를 보존하며 Human 입력을 열지 않는다. lease를 닫은 뒤 옛 Human/AI 명령이 일반 경로로 우회하지 못하는지 검증한다.
- 동시 승계, 이전 Host 복귀, 오래된 저장 재사용 시 유효한 한 진행만 승인한다. 로컬 mock 검증과 온라인 검증 결과를 구분한다.

### E. 4인 확장과 경쟁 적용

- 확정한 캐릭터 수·참여 규칙으로 3·4인 접속, 소유권, 동기화, 이탈·재접속을 검증한다.
- AI 이어하기 이후 현재 인간 참여자만 MMR에 반영하고 불참자 추가 변동이 없음을 검증한다.
- 확정한 이탈 악용 방지 정책, 결과 검증, 결과·MMR 중복 방지를 온라인 권위 기록에서 검증한다.
- 2인 PIE 성공을 4인 지원·Host 승계·온라인 랭크 전체 완료로 기록하지 않는다.

단계 A부터 작은 검증 단위로 진행한다. Steam P2P 우선과 4B 조합을 기준으로 무료 개발 환경·Lobby/Invite와 재접속·MMR의 남은 세부 정책이 필요한 시점에 선택지와 영향을 사용자에게 확인한다. 확정한 번호·AI 전환·3C·5A를 다시 질문하지 않는다.
