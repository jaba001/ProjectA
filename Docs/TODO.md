# 남은 작업과 미결정 제안

아직 구현하지 않은 작업과 결정이 필요한 제안만 둔다. [문서 관리 규칙](../AGENTS.md#문서-관리)을 따른다.

- 구현을 마친 항목은 삭제하고 완료 내용은 커밋 본문에 남긴다. 검수·작동 확인 항목은 [REVIEW](REVIEW.md)에 둔다.
- 제안의 선택 체크는 채택 결과이며 구현 완료가 아니다. 절·제안 번호는 다시 매기거나 재사용하지 않는다.
- 제안은 현재 상태·선택지·권장안·남은 작업·수용 조건 순서로 적는다. 권장안은 자동 채택하지 않는다.

## 4 온라인 협동과 경쟁

Steam·PlayFab 계정, 서비스 ID, 무료 사용 조건이 준비된 뒤 진행한다. 준비 전에는 온라인 SDK 활성화, 인증·저장 성공을 가정한 연결, 유료 리소스 활성화를 하지 않는다. 비용·소유권·저장 권위는 [멀티플레이 계약](MULTIPLAYER.md)을 따른다.

### 4-1 서비스 준비

#### 4-1-1 제안 9 개발 ID와 무료 시험 조건

- 현재: Steam 480 개발 연결 시제품만 있다. 자체 App ID·PlayFab Title·시험 PC 2대는 미준비다. [Steam 예제](https://partner.steamgames.com/doc/sdk/api/example?l=english) · [PlayFab 개발 모드](https://learn.microsoft.com/en-us/xbox/playfab/pricing/development-mode) · [Foundation 조건](https://learn.microsoft.com/en-us/xbox/playfab/get-started/foundation-onboarding)

- [x] 선택 2: 480 개발 설정으로 Steam 세션·P2P 연결 시제품만 먼저 만든다. 자체 앱 인증·PlayFab은 ID와 무료 조건 준비 후 진행한다.

- 남은 작업: ID·권한·한도·시험 계정을 준비하고 UE 5.8 지원 SDK/API를 고정한 뒤 자체 앱 인증을 연결한다. 출시 운영비 조건은 별도로 정한다. [준비 절차](MULTIPLAYER.md#10-t14-8-서비스-준비)

#### 4-1-2 제안 10 초대·재접속·관전

- 현재: Steam 480 개발 모드의 비공개 세션 생성·검색·친구 초대 참가·나가기를 구현했다.

- [x] 선택 1: 비공개 Steam 친구 초대로 새 Run에 참가하고, 원래 참가자는 관리 Run 목록에서 재접속한다. AI로 전환된 원래 소유자는 읽기 전용 관전을 허용한다.

- 남은 작업: 정본 저장(제안 11)을 연결한 뒤 온라인 관리 Run 목록·원래 참가자 재접속·Host 승계 UI·AI 전환 후 읽기 전용 관전을 구현한다.
- 수용 조건: 대체 참가를 거절하고 참가 번호 1~4를 보존한다. 관전자는 계획·Ready·구매·Continue를 바꾸지 못한다.

### 4-2 서비스 구현

#### 4-2-1 제안 11 정본 저장과 동시 승계

- 현재: 같은 PC의 파일·OS lease 개발 어댑터만 있다.

- [x] 선택 1: PlayFab을 쓰는 신뢰 서비스가 Run 본문·원래 소유권·revision/epoch·lease를 함께 승인하고 최신 본문을 제공한다.

- 남은 작업: 조건부 갱신·원자 처리와 무료 범위를 확인하고 계정 인증·멱등 요청·Ready 경계 복구를 연결한다. [복구 계약](MULTIPLAYER.md#6-준비-완료-경계와-파일-저장)
- 수용 조건: 이전 Host 파일 없이 최신 본문을 복구한다. 동시 승계는 한 명만 승인하고 stale revision/epoch 요청은 거절한다.

#### 4-2-2 제안 12 온라인 Snapshot과 상대 선정

- 현재: 로컬 Snapshot 검증과 GameplayTagQuery 조건의 균등 후보 선택 API가 있으나 기본 Run·온라인 공급자와 연결되지 않았다. 장비·전술은 빈 값만 지원한다.

- [x] 선택 1: 현재 지원 범위의 생존 상대·저장 HP·스킬·배치를 먼저 게시하고, 같은 콘텐츠 버전·진행 단계의 태그 조건 후보 중 균등 추첨한다.

- 남은 작업: 게시 시점·보존 기간·중복 상대·버전 변경 처리를 정하고 온라인 게시·보존·매칭·이중 소모 방지·소모품 AI를 구현한다.

#### 4-2-3 제안 13 MMR 집계

- [x] 선택 1: 공격 Run의 PvP 승패를 합산해 파티 공통 변동량을 계산하고 현재 Human에게 동일 적용한다. Snapshot 방어 결과는 통계만 보존한다.

- 남은 작업: 계산식·초기 평점·동률·중도 패배·미확정 결과·이탈 악용 대응을 정하고 서비스 정산을 구현한다.
- 수용 조건: AI·불참자·Snapshot 원소유자에게는 MMR 변동을 주지 않는다.

#### 4-2-4 제안 14 결과 검증과 재실행 방지

- 현재: Listen Host의 전투 권위와 로컬 Ready 저장만 있다.

- [x] 선택 1: 신뢰 서비스가 확정 명령·시드·콘텐츠 버전·판정 입력을 저장하고 전투 종료 후 결과를 재검증한다. 미검증 결과는 MMR에서 제외한다.

- 남은 작업: 서버가 재현할 판정 범위와 실패·이탈·미확정 Attempt 처리를 정하고 구현한다.
- 수용 조건: 같은 Attempt의 중복 제출, 변조된 결과, 오래된 버전의 결과는 정산에서 제외한다.

## 6 신규 에셋 선정과 도입

새로 구입하거나 교체할 콘텐츠와 범위는 미정이다.

- [ ] 구입 대상의 이름·버전·원본 경로와 사용 범위(캐릭터/적·장비·애니메이션·VFX·아이콘/UI)를 기록하고 기존 항목을 유지·교체·미사용으로 구분한다. 참조가 바뀌는 교체 대상은 ID와 기존 저장 처리 정책을 함께 정한다.
- [ ] 채택한 에셋의 UE 5.8 로드·Skeleton/리타깃·소켓/배율·FX 방향을 맞추고 안정 ID·표시명·태그·실행 프로필·카탈로그를 갱신한다. GameplayTag 조건·GAS·서버 피해 권위는 유지한다.
- [ ] 프리뷰·공격/피격·장비·UI·저장·원격 표현에 적용한다. 교체 후 미사용 에셋은 참조·저장 호환을 확인하고 Unreal 기능으로 정리한다.

## 32 기획 폴리싱

시스템은 대부분 갖췄지만 각 시스템에서 플레이어가 고민할 선택이 적다. 이 절은 선택의 무게를 늘리는 제안을 모은다.

- 설계 방향: 체력을 아끼며 진행하는 구조(Slay the Spire 2 방식)를 따른다. 전멸 시 Run 종료와 전투 사이 체력 이월 규칙은 유지한다.
- 제안의 수치(비용·가격·확률·보너스)는 구조 예시다. 최종 값은 [31절](#31-핵심-재미와-밸런스)에 따라 사용자가 정한다.
- 권장 착수 순서: 제안 21·22(전투 판단) → 제안 24(빌드 축, [ITEM_DESIGN](ITEM_DESIGN.md)) → 제안 28(경로의 위험·보상) → 나머지.

### 32-1 제안 21 적 행동 예고

- 현재: 적 계획은 인간 계획보다 먼저 고정한다. 우측 상단 패널에 선택한 적 하나의 HP와 계획만 표시한다. 전장에서 적이 누구를 노리는지 한눈에 볼 수 없다.

- [ ] 선택 1: Planning 동안 모든 적의 대상(선 또는 표식)과 사용할 스킬 아이콘을 전장에 표시한다.
- [ ] 선택 2: 노려지는 아군 머리 위에 경고 표식만 표시하고 스킬은 공개하지 않는다.
- [ ] 선택 3: 현재 패널 표시를 유지한다.

- 권장: 선택 1. 이미 고정된 계획 데이터를 보여주기만 하면 매 라운드가 "누구를 먼저 끊을까"를 푸는 퍼즐이 된다. 빙결·스턴의 행동 취소와 SAP 이동 회피의 가치도 함께 올라간다.
- 영향: 혼란으로 대체될 명령, 대상 사망 시 재선택처럼 실행 중 바뀌는 부분은 "예정"으로 구분해 표시해야 한다.
- 수용 조건: 표시는 서버가 고정한 계획의 복제값만 읽고 판정에 관여하지 않는다. 협동 클라이언트와 Snapshot 상대에도 같게 표시된다.

### 32-2 제안 22 행동 순서 표시

- 현재: 시작 지연은 속도 차로 Planning에서 고정되지만 화면에 순서가 없다. 파티 카드에는 확정 턴 순서를 추가하지 않기로 했다([UI_README](UI_README.md)).

- [ ] 선택 1: 상단에 양 팀 유닛의 시작 지연 순서를 보여주는 타임라인 막대를 둔다. 파티 카드 결정은 유지한다.
- [ ] 선택 2: 각 유닛 머리 위에 행동 순번 숫자만 표시한다.
- [ ] 선택 3: 표시하지 않는다.

- 권장: 선택 1. 속도(민첩)가 행동 순서를 정하므로 순서가 보여야 냉각·속도 성장의 가치를 체감한다.
- 수용 조건: 냉각 등으로 다음 라운드에 반영될 속도 변화는 현재 라운드 순서와 구분한다.

### 32-3 제안 23 스킬 비용·선딜 차등

- 현재: 공격 스킬 비용은 모두 AP 1·SAP 0이고 선딜은 무기 근접 0.23초·마법 무기 1초·나머지 0.3초다([SKILL_BALANCE](../DataCatalogs/SKILL_BALANCE.csv)). 위력과 마법 시전 시간 외에는 스킬을 고를 이유가 적다.

- [ ] 선택 1: 범위·등급에 따라 AP·SAP·선딜을 차등한다(예: 범위 스킬은 선딜이 길고, 강한 스킬은 SAP를 함께 소모해 이동과 경쟁).
- [ ] 선택 2: 라운드 AP를 늘려 약한 스킬 여러 개와 강한 스킬 하나 중 고르게 한다.
- [ ] 선택 3: 비용을 유지하고 위력만으로 구분한다.

- 권장: 선택 1. 기존 CSV 열과 Run 생성 시 고정 경로를 그대로 쓰고, 선딜 차이가 시간차 전투에서 "빠른 약공 vs 느린 강공" 판단을 만든다.
- 수용 조건: 비용은 기존처럼 잠금 시 한 번 차감하고 환불하지 않는다. 이전 Run 저장은 저장된 수치를 유지한다.

### 32-5 제안 25 직업 정체성

- 현재: 네 직업 모두 HP 100이며 시작 무기와 힘·민첩·지능이 다르다(전사 10/5/1·마법사 1/5/10·궁수 5/7/4·도적 5/10/1, [GAME_STATUS 5절](GAME_STATUS.md#5-직업과-능력치)). 고유 패시브는 없다.

- [ ] 선택 1: 직업별 시작 HP를 차등하고 고유 패시브 1개를 준다(예: 전사 피해 감소, 도적 선제 속도, 궁수 원거리 피해, 마법사 상태이상 수치 증가).
- [ ] 선택 2: 시작 HP만 추가로 차등한다.
- [ ] 선택 3: 현재 능력치와 시작 무기로만 구분한다.

- 권장: 선택 1. 민첩이 행동 순서를 정하고 힘·지능이 피해를 나눠 이미 역할이 갈리며, 패시브가 무기 선택의 방향을 잡아준다.
- 수용 조건: 패시브는 제안 24와 같은 태그·GAS 구조를 쓴다. 기존 저장은 저장된 직업 수치를 유지한다.

### 32-6 제안 26 Snapshot 승리 보상

- 현재: Snapshot 전투에는 성장·아이템·골드·휴식이 없고 패배하면 Run이 끝난다. 위험만 있고 이길 이유가 진행 외에는 없다.

- [ ] 선택 1: 승리 시 골드 또는 아이템 3택1을 준다. 남긴 HP 비율이 높을수록 보상을 올린다.
- [ ] 선택 2: 승리 시 휴식 회복만 준다.
- [ ] 선택 3: 보상 없이 유지한다.

- 권장: 선택 1. 체력 보존 방향과 맞물려 "피해 없이 이기는" 플레이에 보상을 준다.
- 영향: 보상 상태 저장(`GoldRewardState`)과 보상 수령자 규칙을 Snapshot 노드에도 적용한다.
- 수용 조건: 기존 PvE 보상 경로·저장 검증을 재사용하고, 보상 공개 전 실패 시 동일 재시도가 된다.

### 32-7 제안 27 난이도 경로 보상 차등

- 현재: 하·중·상은 같은 편성에 체력·속도·골드 배율만 다르다([PVE_DIFFICULTIES](../DataCatalogs/PVE_DIFFICULTIES.csv)). 상 난이도를 고를 이유가 골드뿐이다.

- [ ] 선택 1: 상 난이도일수록 보상 아이템의 등급 가중치를 올린다.
- [ ] 선택 2: 상 난이도일수록 보상 선택지 수를 늘린다(3 → 4).
- [ ] 선택 3: 골드 배율만 유지한다.

- 권장: 선택 1. 체력을 걸고 더 좋은 장비를 얻는 Slay the Spire의 엘리트 판단과 같은 구조다. 기존 등급 추첨에 난이도별 가중치 행만 더하면 된다.
- 수용 조건: 가중치는 CSV/DataAsset 데이터로 두고 Run 생성 시 저장한다.

### 32-8 제안 28 인카운터 위험·보상 노드

- 현재: 인카운터 60회 중 회복의 샘물·부활소를 뺀 대부분이 상점이다([ENCOUNTER_POOL](../DataCatalogs/ENCOUNTER_POOL.csv)). 문 3개 너머가 무엇인지 고르기 전에 알 수 없어 경로를 계획하기 어렵다.

- [ ] 선택 1: 위험·보상 노드를 추가한다. 엘리트 전투(체력 소모·좋은 보상), 휴식처(회복 또는 장비 강화 중 택1), 선택 이벤트(HP를 내고 아이템 획득 등).
- [ ] 선택 2: 노드 종류는 유지하고 묶음당 인카운터 수를 줄여 반복감을 낮춘다.
- [ ] 선택 3: 선택 1과 2를 함께 진행한다.

- 권장: 선택 1. 휴식처의 "회복 vs 강화"는 체력 보존 설계의 핵심 판단이다. 문에 노드 종류를 미리 표시하면 경로 계획이 생긴다. 인카운터 수 조정은 31절의 Run 길이 결정과 함께 정한다.
- 수용 조건: 새 노드는 기존 그룹·변형 가중치 추첨과 RunId 시드 고정을 따르고 태그로 분류한다.

### 32-10 제안 30 전투 피드백

- 현재: 피해 숫자·상태이상 수치 표시·타격 연출이 없다.

- [ ] 선택 1: 피해·회복·보호막 숫자와 유닛 머리 위 상태이상 아이콘·수치를 표시한다.
- [ ] 선택 2: 선택 1에 타격 정지(hit stop)·카메라 흔들림·처치 연출을 더한다.
- [ ] 선택 3: 현재 표현을 유지한다.

- 권장: 선택 2. 체감 완성도가 가장 크게 오르는 영역이며 상태이상 빌드(제안 24)를 읽으려면 수치 표시가 필요하다.
- 수용 조건: 표시는 서버 판정 결과의 복제값만 사용하고 협동 클라이언트에서도 같게 보인다.
