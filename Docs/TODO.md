# 남은 작업

**남은 오류와 미확인 항목을 우선 처리한다.** 새 콘텐츠는 게임 규칙과 디자인을 확정한 뒤 구현한다.

갱신일: 2026-09-17. 완료 이력은 [HISTORY](HISTORY.md), 현재 구현은 [PROJECT_PLAN](PROJECT_PLAN.md)에서 확인한다.

작업 우선순위·구현 방식·코드 검토·컴파일·문서 정리·커밋과 push는 Codex가 맡는다. 개별 코드 변경마다 사용자 지시나 검수를 기다리지 않는다. 미정 기획은 번호가 있는 선택지와 권장안을 제시하고 사용자가 선택한 뒤 기준 문서와 구현에 반영한다. 원래 소유권·비용 제한·명시적으로 보류한 랭크 정책은 유지한다. 기존 시험값을 검증된 최종 밸런스로 기록하지 않는다.

**선택 방법:** 제안 항목 아래의 선택지 중 하나만 체크한다. 선택 체크는 채택 요청이며 작업 완료 표시가 아니다. 번호로 전달할 때는 `3-1-1: 1, 3-1-2: 2`처럼 항목과 선택 번호를 지정한다. 권장안도 선택 전에는 적용하지 않는다. 미선택은 대기하고 복수 선택은 충돌로 보류한다.

**작업 요청:** 체크 결과가 이 파일에 반영된 뒤 `TODO 진행해줘`로 요청한다. Codex는 이 문서에서 선택 결과·작업 범위·우선순위를 파악하고, 필요한 코드와 검증 기준을 확인하여 진행한다. 선택 후에는 항목 상태를 `작업 대기 → 작업 중 → 구현 완료·사용자 검증 대기 → 완료`로 갱신한다. 문서만 변경하는 항목은 정적 검사 후 완료할 수 있다. 일반 작업 목록의 체크는 완료 표시이며 제안 선택지의 체크와 구분한다.

**체크 저장 기준:** 로컬 `Docs/TODO.md`에 저장된 체크를 읽는다. 2026-09-16 Windows의 `.md` 연결 프로그램이 Notion인 것은 확인했으며, Notion에서 편집한 내용이 원본 파일에 저장되는지는 미확인이다. 원본에 직접 저장되면 별도 계정 연동이나 페이지 주소가 필요 없다. 작업 요청 시 파일에 나타난 체크만 반영하며, Notion 복사본에만 남은 변경은 읽었다고 가정하지 않는다. 원본에 저장되지 않는 방식이면 수정한 Markdown을 이 파일에 반영하거나 별도 페이지 연결을 설정해야 한다.

진행 순서는 오류 수정과 데이터 사전 검사 → 전투·아이템·Run 규칙의 기본안 → 최소 아이템·직업·상점 기능 → 상태이상·AI·표현 → 실제 서비스 연동이다. 외부 계정·비용 또는 사용자 실행 결과가 필요한 항목은 의존하는 작업만 대기한다. 작동 확인은 아래 남은 항목만 정리한다.

## 3 게임 규칙 결정

**이 절은 구현 전에 결정할 기획이다.** 시간차 전투와 집중 자원 제외를 유지하며, 집중 효과를 AP 회복이나 추가 행동으로 자동 치환하지 않는다. 현재 시험값을 최종 규칙으로 간주하지 않는다.

### 3-1 전투 규칙

아래 4개는 바로 선택할 수 있는 제안이다. 나머지 결정 항목도 관련 구현 전에 같은 형식으로 제시한다. 체크하지 않은 권장안은 현재 코드를 변경하지 않는다.

#### 3-1-1 이동 후 최종 배치

상태: 선택 대기. 현재는 다른 생존 유닛의 복귀 칸이나 예약 목적지와 겹치면 계획 잠금을 거절한다.

- [ ] **1. 복귀·예약 칸 중복 금지 유지 — 권장.** 한 칸에 한 유닛만 남고 복귀 위치를 예측할 수 있다. 자리를 교환하는 이동은 허용하지 않는다.
- [ ] **2. 이번 라운드에 비워질 칸으로 이동·자리 교환 허용.** 모든 생존 유닛의 최종 칸은 달라야 한다. 이동 취소·사망 시 배치 복구와 추가 예약 검사가 필요하다.

선택 후 작업: 서버 계획 잠금과 복귀·취소 처리를 선택한 배치 규칙에 맞춘다. 수용 조건은 최종 중복 점유 없음, 일반 공격자 복귀, 상대 진영 잔류 금지다. 유닛 간 이동 통과는 두 안에서 유지한다.

#### 3-1-2 같은 시각의 피해 공격

상태: 선택 대기. 현재는 안정적인 서버 순서대로 피해·사망을 즉시 반영한다.

- [ ] **1. 서버 순서대로 즉시 처리.** 현재 구조를 유지한다. 동일 판정 시각에도 먼저 처리된 치명타격이 뒤 공격을 취소할 수 있다.
- [ ] **2. 같은 판정 시각의 피해 공격을 함께 적용 — 권장.** 해당 시각 시작에 유효한 공격들의 충돌을 먼저 판정한 뒤 피해를 함께 반영하여 등록 순서의 유불리를 줄인다. 동시 처치와 피해 일괄 처리가 추가된다.

선택 후 작업: 동일한 서버 판정 시각의 충돌·피해·사망 순서를 구현하고 상호 치명타격을 확인한다. 행동 시작 시각만 같다고 동시 적중을 보장하지 않으며, 더 이른 시각에 사망한 유닛의 미발동 공격은 계속 취소한다. 지원·상태효과의 세부 순서는 별도 제안 대상이다.

#### 3-1-3 계획 수정 시 준비 해제

상태: 선택 대기. 현재는 인간 팀원 전원의 준비를 해제하고 잠금 전 준비 취소를 허용한다.

- [ ] **1. 인간 팀원 전원의 준비 해제 — 권장.** 변경된 협동 계획을 모두 재확인한다. 계획을 자주 수정하면 준비 클릭이 늘어난다.
- [ ] **2. 수정한 소유자만 준비 해제.** 다른 팀원의 준비를 유지하여 클릭을 줄인다. 다른 사람의 수정 내용을 재확인하지 않은 채 전투가 시작될 수 있다.

선택 후 작업: 계획 수정·준비 취소·동시 요청의 서버 상태와 화면 표시를 맞춘다. 수용 조건은 잠금 전 취소 가능, 원래 캐릭터 소유권 유지, 유효한 모든 계획과 필요한 준비가 갖춰진 뒤에만 시작이다.

#### 3-1-4 양 팀 전멸

상태: 선택 대기. 현재는 승패·보상을 확정하지 않고 전투를 중단한다.

- [ ] **1. 패배로 Run 종료 — 권장.** 승리 보상을 지급하지 않고 기존 패배 흐름을 사용한다. 플레이어에게는 패배로 표시한다.
- [ ] **2. 무승부로 표시하고 Run 종료.** 승리 보상을 지급하지 않으며 새 결과 표시·저장 구분이 필요하다.

선택 후 작업: 잔여 공격과 복귀 정리 후 결과를 한 번만 확정하고 저장·결과 화면을 연결한다. 수용 조건은 중단 상태 해소와 승리 보상 중복 지급 없음이다. 경쟁 MMR·별도 패배 보상·재전투 정책은 이 선택으로 확정하지 않는다.

**후속 제안 대상:** 아래 항목은 구현 전에 선택 가능한 안과 수용 조건을 추가한다.

- [ ] **행동 비용과 추가 속도 보정의 최종 규칙을 정한다.** 민첩과 전투 시작 속도의 1:1 관계는 사용자 요청으로 확정했으며 근접 접근·복귀는 [초기 튜닝](GAME_DESIGN.md#8-4-공격-접근과-복귀)을 적용한다. AP/보조 AP의 계획 시작 초기화·잠금 시 차감·불발 시 미환불을 검토한다. SAP·비근접 이동·시전·투사체 속도 보정, 속도 비율 정규화와 대기 시간 상한은 후속 기획으로 둔다.
- [ ] **엄호와 상태이상의 처리 경계를 정한다.** 엄호의 중첩·지속·전열 보호, 해로운 상태이상 8종의 발동·감소·해제와 이동·피격·동시 처리 시점을 확정한다. [상태별 미정 사항](STATUS_EFFECTS.md)
- [ ] **AI 전술과 적 의도의 공개 범위를 정한다.** 지원 대상·우선순위, 자기 진영에 남을 이동 좌표와 예약 충돌, Guard·MoveShot·GroundStrike의 AI 후보 편입 여부를 결정한다. 부분 공개·위치 협공은 후속 기획으로 둔다. 인간 초안 이전 AI 계획 고정은 유지한다.
- [ ] **라운드 중단 후 복구할 시점과 데이터를 정한다.** 시전·좌표·투사체·지연 피해·난수·이미 적용한 결과의 복구 범위와 재실행 악용 방지 규칙을 설계한다. 이전 순차 전투의 저장·복구 경로는 재도입하지 않는다.

현재 규칙과 시험값의 상세는 [전투 기획](GAME_DESIGN.md#8-라운드-계획과-시간차-자동-전투)을 따른다.

- [ ] **첫 구현에 사용할 아이템과 직업 스킬을 고른다.** 후보 묶음, 직업별 시작 스킬·효과·피해/회복량·시전/비행/접근 수치·AP/보조 AP 비용을 확정한다. 원작 수치와 ProjectA 수치를 구분한다. [직업 제안](GAME_DESIGN.md#6-1-직업-역할-보충-제안) · [도입 순서 제안](GAME_DESIGN.md#7-10-조합-예시와-도입-순서)
- [ ] **원작 완전 성공 부가 효과의 변환 조건을 정한다.** 관통·상태 부여 등 원작의 성공 슬롯에 의존하는 효과를 스킬별로 변환하거나 제외한다. 충돌 적중을 원작의 완전 성공으로 자동 치환하지 않는다.
- [ ] **장비 슬롯과 무기 교체 규칙을 정한다.** 손 장비 포함 여부·양손 무기 점유, 무기 스킬과 직업 스킬의 대체/병존을 결정한다. 장착·교체·거래 가능 시점, 전투 중 비용, 출처별 스킬 부여·회수 기준도 정한다.
- [ ] **회복 모델과 파이프 효과를 정한다.** C01 고정량 또는 C02 비율형 회복을 선택한다. 파이프·재질의 발동 조건·효과 소유자·중첩 규칙을 정한다.
- [ ] **아이템·재화의 소유와 거래 권한을 정한다.** 개인/공동 재고·재화, 장비 배분과 구매 권한을 결정한다. 아이템 소유와 캐릭터의 원래 소유권을 구분한다.
- [ ] **상점 상품과 보상 생성 규칙을 정한다.** 상점별 역할·수량·가격, 필수 보급과 역할 보완 여부, 후보 가중치·출현 조건·중복·새로고침 규칙을 결정한다.
- [ ] **Run 동안 유지할 성장과 지급 범위를 정한다.** 장비·스킬·보상·사탕·파이프·소모품을 누적할지 전투마다 재지급할지 정한다. 계정 영구 성장으로 자동 확대하지 않는다.
- [ ] **참조 아이템의 미확인 수치를 대조한다.** 설치본 Build `24247341`의 도감·카드로 피해·가격·재장전·지속/중첩·면역·정화·파이프 발동을 확인한다. A05~A07은 FTK1 기준 아이템과 수치를 지정하며 FTK2 동명 항목으로 대체하지 않는다. [참조 근거](GAME_DESIGN.md#7-11-ftk2-설치본-근거와-해석-범위)

### 3-3 Run 진행

- [ ] **패배와 사망 후 진행 방식을 정한다.** 즉시 Run 종료를 유지할지, 패배 횟수나 Run 생명력을 둘지 결정한다. 패배 보상, 누적 HP·사망·회복·소모품과 저장 시점도 함께 정한다.
- [ ] **인원별 캐릭터 배정과 Run 길이를 정한다.** 1인당 캐릭터 수·부족 시 배정, 라운드 수·목표 플레이 시간·마지막 인카운터를 결정한다.

## 4 온라인 협동과 경쟁

**T14는 Steam·PlayFab 서비스 준비와 실제 연동이 필요하다.** 비용·소유권·저장 권위의 기준은 [멀티플레이 계약](MULTIPLAYER.md)을 따른다.

### 4-1 서비스 준비

- [ ] **Steam App ID와 PlayFab Title을 준비한다(T14-8).** 실제 인증·연결에 사용할 개발 환경을 정한다. 공용 Steam ID 480 시험안은 채택·실행 전이다. [준비 항목](MULTIPLAYER.md#t14-8-서비스-준비)
- [ ] **무료 개발 시험 범위와 출시 비용 조건을 정한다.** 무료 한도 내 시험과 출시 후 운영비를 구분한다. 유료 리소스는 임의로 활성화하지 않는다.
- [ ] **초대·재접속·관전 흐름을 정한다.** Lobby/Invite, 재접속 후 준비 과정, AI로 전환된 캐릭터 소유자의 관전 허용 여부를 결정한다.

### 4-2 서비스 구현과 검증

- [ ] **Steam 인증·P2P 접속과 협동 화면을 연결한다.** 실제 계정과 원래 참가자를 확인하고 초대·참가·관리 Run 재개·Host 승계 화면을 구현한다. 개발용 새 방 UI와 관리 Run 재개를 구분한다.
- [ ] **여러 PC에서 같은 Run을 안전하게 저장한다.** 정본 저장 위치와 인증 방식을 정하고, 중복 실행·동시 승계를 한 번만 승인하도록 처리한다. 라운드 복구는 [3-1절](#3-1-전투-규칙)의 결정 후 연결한다.
- [ ] **상대 전투 데이터의 온라인 저장·매칭을 구현한다.** Snapshot에 포함할 장비·소모품·성장·속도·전술과 콘텐츠 버전을 정한다. AI 사용량·소모 반영, 전송·보존·버전 변환과 데이터 검증을 설계한다.
- [ ] **경쟁 점수와 결과 검증을 설계한다.** MMR 반영 대상 확정 시점·계산/정산 단위·공격/방어 결과를 정한다. 고의 이탈·턴 반복·중복 결과·위변조를 막을 책임과 방식을 결정한다.
- [ ] **T14의 실제 서비스 수용 조건을 검증한다.** 저장된 상대 Snapshot으로 새 라운드 전투를 실행하고, 최소 2인에서 소유권·계획·행동 시작 시각·실제 위치·HP/AP·사망·결과가 일치하는지 확인한다. 로컬 모의 저장소나 같은 PC의 PIE 결과를 서비스 연동 검증으로 대체하지 않는다.

P2P 연결과 중앙 저장·계정 인증·MMR 검증은 각각 필요하다. 이전 Combat 저장 복원은 지원 범위에 포함하지 않는다.

## 5 디자인 확정 후 구현할 일

**아래 작업은 필요한 기획·시각 디자인이 확정될 때까지 보류한다.** 각 항목의 선행 조건을 충족한 뒤 구현한다.

- [ ] **아이템 데이터와 거래 기능을 구현한다.** [3-2절](#3-2-아이템과-직업)의 슬롯·회복·소유·장착·가격 규칙을 먼저 확정한다. 정적 정의·Run 인스턴스·성장 상태·명령·Snapshot 필드를 설계하고 기존 DataAsset·USTRUCT·USaveGame·GAS를 확장한 뒤 사용자 작동 검증을 진행한다.
- [ ] **네 직업별 실제 스킬 프로필을 연결한다.** 직업 목록과 공통 시작 능력치는 [6-2절](GAME_DESIGN.md#6-2-네-직업과-공통-시작-능력치)로 확정했다. 전사·마법사·궁수·도적의 스킬 목록·수치·장비·성장 차이는 별도 결정하며 미작성 공격을 임의로 채우지 않는다. 기존 공격 변환이 처리하지 못하는 회복·버프·몽타주 효과는 명시 프로필로 연결한다.
- [ ] **상태이상과 지원·이동 AI 전술을 구현한다.** [3-1절](#3-1-전투-규칙)의 발동·중첩·이동 경계와 선택 우선순위, 검증할 기대 결과를 먼저 확정한다.
- [ ] **아이콘·모델·애니메이션·VFX를 제작한다.** 직업/스킬별 표현 목록과 제작 사본 경로, 서버의 타격·발사·복귀 시점에 연결할 방법을 먼저 확정한다. 애니메이션 알림에 피해 권위를 넘기지 않는다.
- [ ] **최종 UI 디자인을 적용한다.** 계획·대상·비용·오류·적 의도의 정보 우선순위와 선택/비활성 표시, 화면 비율별 배치 시안을 먼저 확정한다. 기존 입력·소유권·공통 DPI 기준을 유지한다.
