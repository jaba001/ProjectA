# 남은 작업

**새 에셋 구입에 맞춰 콘텐츠 도입 계획을 재정리한다.** 구입 팩·유지/교체 범위는 미정이며 [6절](#6-신규-에셋-선정과-도입)을 따른다. 기존 팩의 전수 검토·수량 확대는 도입 선행 조건에서 제외하고 공통 기능의 오류·미확인 사항은 계속 처리한다.

갱신일: 2026-10-01. 완료 이력은 [HISTORY](HISTORY.md), 현재 구현은 [PROJECT_PLAN](PROJECT_PLAN.md)에서 확인한다.

작업 우선순위·구현 방식·코드 검토·컴파일·문서 정리·커밋과 push는 Codex가 맡는다. 개별 코드 변경마다 사용자 지시나 검수를 기다리지 않는다. 미정 기획은 번호가 있는 선택지와 권장안을 제시하고 사용자가 선택한 뒤 기준 문서와 구현에 반영한다. 원래 소유권·비용 제한·명시적으로 보류한 랭크 정책은 유지한다. 기존 시험값을 검증된 최종 밸런스로 기록하지 않는다.

**선택 방법:** 제안 항목 아래의 선택지 중 하나만 체크한다. 선택 체크는 채택 요청이며 작업 완료 표시가 아니다. 번호로 전달할 때는 `3-1-1: 1, 3-1-2: 2`처럼 항목과 선택 번호를 지정한다. 권장안도 선택 전에는 적용하지 않는다. 미선택은 대기하고 복수 선택은 충돌로 보류한다.

**작업 요청:** 체크 결과가 이 파일에 반영된 뒤 `TODO 진행해줘`로 요청한다. Codex는 이 문서에서 선택 결과·작업 범위·우선순위를 파악하고, 필요한 코드와 검증 기준을 확인하여 진행한다. 선택 후에는 항목 상태를 `작업 대기 → 작업 중 → 구현 완료·사용자 검증 대기 → 완료`로 갱신한다. 문서만 변경하는 항목은 정적 검사 후 완료할 수 있다. 일반 작업 목록의 체크는 완료 표시이며 제안 선택지의 체크와 구분한다.

**체크 저장 기준:** 로컬 `Docs/TODO.md`에 저장된 체크를 읽는다. 2026-09-16 Windows의 `.md` 연결 프로그램이 Notion인 것은 확인했으며, Notion에서 편집한 내용이 원본 파일에 저장되는지는 미확인이다. 원본에 직접 저장되면 별도 계정 연동이나 페이지 주소가 필요 없다. 작업 요청 시 파일에 나타난 체크만 반영하며, Notion 복사본에만 남은 변경은 읽었다고 가정하지 않는다. 원본에 저장되지 않는 방식이면 수정한 Markdown을 이 파일에 반영하거나 별도 페이지 연결을 설정해야 한다.

진행 순서는 오류 수정과 준비 완료 저장·복구 → 확정 전투 규칙 → 최소 아이템·직업·상점 기능 → AI·표현 → 후순위 상태이상 → 실제 서비스 연동이다. 엄호는 기획·구현 대상에서 제거했다. 비근접 시전·이동과 투사체의 민첩 연동은 별도 보류하며 현재 투사체 공통 감속은 2-37절에서 확인한다. 외부 계정·비용 또는 사용자 실행 결과가 필요한 항목은 의존하는 작업만 대기한다. 작동 확인은 아래 남은 항목만 정리한다.

## 1 사용자 작동 확인

기존 에셋에 의존하는 표현 확인은 새로 채택한 대상에 연결한 뒤 수행한다. 현재 코드의 남은 확인은 [2절](#2-오류-수정-후-확인)의 미완료 항목을 따른다. 작동 테스트는 사용자가 수행하며 별도 실행 요청이 없는 작업에서는 Codex가 PIE·게임·자동화 테스트를 시작하지 않는다. 컴파일·정적 검사와 실제 작동 확인을 구분한다.

완료 체크 18개와 이전 외형 구성은 [이관 이력](HISTORY.md#9-todo-완료-항목-이관)에 보존했다. 2026-09-16 일반 플레이 보고와 2026-09-18 위임 실행은 당시 범위의 결과이며 최신 변경·협동 예외·서비스 연동의 완료를 의미하지 않는다.

- [ ] **2. 기존 저장은 기존 콘텐츠를 유지.** 새 Run부터 새 에셋을 사용하고 기존 저장용 원본·cook 참조를 유지한다. 두 콘텐츠 구성의 용량·관리 비용이 남는다.
- [ ] **3. 교체 버전과 맞지 않는 저장은 명시적으로 거절.** 원본 파일을 보존하고 새 Run 안내를 표시한다. 매핑 부담은 줄지만 해당 저장의 재개를 지원하지 않는다.

선택 후 작업: 적용 대상 BodyId·클래스 경로·아이템/스킬 ID·PrimaryAssetId·Snapshot 콘텐츠 버전을 기록하고 읽기 후보 검증과 안내를 연결한다. 권장안은 자동 적용하지 않는다. 수용 조건은 원본 파일 보존·다른 상태 불변·중복 지급 없음과 선택한 복원/거절 결과의 일치다.

### 3-3 Run 진행

2026-09-22 사용자 확정: 목표 플레이 시간은 고정하지 않는다. **인카운터 3회 → 몬스터 PvE 1회 → 인카운터 3회 → Async PvP 1회**를 10회 반복한다. 정상 완주 시 인카운터 60회·PvE 10회·PvP 10회이며, 각 인카운터의 후보 3개 중 하나 선택 규칙을 유지한다. 목표 순서·횟수는 확정했지만 단계별 풀·편성·성장/보상·PvP 연결 규칙이 미정이므로 전체 Run 구현은 대기다. 현재 10전투·상점 9회의 시험 Run과 구분한다. [목표 Run](GAME_DESIGN.md#2-목표-run과-현재-구현)

- [ ] **Run 내 사망·회복·소모품의 세부 규칙을 정한다.** 양 팀 전멸은 패배·Run 종료·승리 보상 없음으로 확정했다. Run 중 누적 HP·사망·소모품의 처리와 추후 회복·부활 인카운터의 연결을 결정한다. Run 종료 후 성장·재화·아이템 보상은 없으며 MMR의 패배·이탈 계산은 별도 기획이다.
- [ ] **협동 인원별 캐릭터 배정을 정한다.** 1인당 캐릭터 수·부족 슬롯 배정을 결정한다. 일반 싱글의 직접 조작 1명·나머지 동료 AI 정책은 유지한다.
- [ ] **확정한 Run 구성을 구현한다.** 단계별 인카운터 풀·PvE 편성·난이도·성장/보상과 PvP 연결 규칙을 결정한 뒤 진행·저장·UI에 연결한다. 수용 조건은 새 Run이 인카운터부터 시작하고 정상 완주 시 정해진 순서와 횟수를 충족하며, 재개 후에도 진행 위치와 이미 확정한 선택을 유지하는 것이다. 현재 구현은 10전투·상점 9회의 시험 Run이다.

## 4 온라인 협동과 경쟁

**T14는 Steam·PlayFab 서비스 준비와 실제 연동이 필요하다.** 계정·서비스 ID·비용 조건과 온라인 권위 정책이 준비되지 않은 항목은 외부 준비/결정 대기다. 로컬 코드·문서 점검은 독립적으로 진행하되 서비스 활성화·실제 연결 완료로 기록하지 않는다. 비용·소유권·저장 권위의 기준은 [멀티플레이 계약](MULTIPLAYER.md)을 따른다.

### 4-1 서비스 준비

- [ ] **Steam App ID와 PlayFab Title을 준비한다(T14-8).** 실제 인증·연결에 사용할 개발 환경을 정한다. 공용 Steam ID 480 시험안은 채택·실행 전이다. [준비 항목](MULTIPLAYER.md#t14-8-서비스-준비)
- [ ] **무료 개발 시험 범위와 출시 비용 조건을 정한다.** 무료 한도 내 시험과 출시 후 운영비를 구분한다. 유료 리소스는 임의로 활성화하지 않는다.
- [ ] **초대·재접속·관전 흐름을 정한다.** Lobby/Invite, 재접속 후 준비 과정, AI로 전환된 캐릭터 소유자의 관전 허용 여부를 결정한다.

### 4-2 서비스 구현과 검증

- [ ] **Steam 인증·P2P 접속과 협동 화면을 연결한다.** 실제 계정과 원래 참가자를 확인하고 초대·참가·관리 Run 재개·Host 승계 화면을 구현한다. 개발용 새 방 UI와 관리 Run 재개를 구분한다.
- [ ] **여러 PC에서 같은 Run을 안전하게 저장한다.** 정본 저장 위치와 인증 방식을 정하고, 중복 실행·동시 승계를 한 번만 승인하도록 처리한다. [준비 완료 복구 계약](#3-1-전투-규칙)을 온라인 정본 저장에 연결한다.
- [ ] **상대 전투 데이터의 온라인 저장·매칭을 구현한다.** Snapshot에 포함할 장비·소모품·성장·속도·전술과 콘텐츠 버전을 정한다. AI 사용량·소모 반영, 전송·보존·버전 변환과 데이터 검증을 설계한다.
- [ ] **경쟁 점수와 결과 검증을 설계한다.** Run 종료 시 MMR만 반영하는 방향은 확정했다. 반영 대상 확정 기준·시점, 계산식·개별 PvP 결과의 합산 방식·공격/방어 결과 반영을 정한다. 고의 이탈·턴 반복·중복 결과·위변조를 막을 책임과 방식을 결정한다.
- [ ] **T14의 실제 서비스 수용 조건을 검증한다.** 저장된 상대 Snapshot으로 새 라운드 전투를 실행하고, 최소 2인에서 소유권·계획·행동 시작 시각·실제 위치·HP/AP·사망·결과가 일치하는지 확인한다. 로컬 모의 저장소나 같은 PC의 PIE 결과를 서비스 연동 검증으로 대체하지 않는다.

P2P 연결과 중앙 저장·계정 인증·MMR 검증은 각각 필요하다. 이전 Combat 저장 복원은 지원 범위에 포함하지 않는다.

## 5 디자인 확정 후 구현할 일

**아래 작업은 필요한 기획·시각 디자인이 확정될 때까지 보류한다.** 각 항목의 선행 조건을 충족한 뒤 구현한다.

- [ ] **아이템 데이터와 거래 기능을 확장한다.** [아이템상점 시험](#2-31-아이템상점-시험)의 보유·구매·리롤을 기반으로 확정한 [장비 슬롯](GAME_DESIGN.md#2-2-장비-슬롯과-장비-부여-스킬)과 [3-2절](#3-2-아이템과-직업)의 회복·소유·장착/교체·스킬 연결·가격 세부 규칙을 먼저 확정한다. 정적 정의·Run 인스턴스·성장 상태·명령·Snapshot 필드를 확장하고 기존 DataAsset·USTRUCT·USaveGame·GAS를 활용한 뒤 사용자 작동 검증을 진행한다.
- [ ] **채택한 에셋으로 네 직업별 스킬 프로필을 연결한다.** 직업 목록과 공통 시작 능력치는 [6-2절](GAME_DESIGN.md#6-2-네-직업과-공통-시작-능력치)로 확정했다. 즉시 GE_Heal·라운드 한정 GE_Shield·명시 CastMontage는 구현했으며 실제 확인은 2-36절을 따른다. 전사·마법사·궁수·도적의 스킬 목록·수치·장비·성장 차이와 추가 버프/지속 효과는 별도 결정하며 미작성 공격을 임의로 채우지 않는다.
- [ ] **지원·이동 AI 전술을 구현한다.** [3-1절](#3-1-전투-규칙)의 대상·이동 경계·선택 우선순위와 검증할 기대 결과를 먼저 확정한다.
- [ ] **구입 에셋의 아이콘·모델·애니메이션·VFX를 연결한다.** [6절](#6-신규-에셋-선정과-도입)의 채택 범위와 원본 참조·필수 파생 결과, 서버의 타격·발사·복귀 시점을 먼저 확정한다. 구입 팩의 Blueprint 실행 규칙을 현재 GAS·태그·서버 권위 대신 자동 채택하지 않는다. 애니메이션 알림에 피해 권위를 넘기지 않는다.
- [ ] **채택한 UI 에셋으로 최종 디자인을 적용한다.** UI 팩·아이콘·폰트·배경의 적용 범위를 선정하고 계획·대상·비용·오류·적 의도의 정보 우선순위와 선택/비활성 표시, 화면 비율별 배치 시안을 먼저 확정한다. 기존 입력·소유권·공통 DPI 기준을 유지한다.
- [ ] **상태이상을 구현한다 — 후순위.** 기본 전투·준비 완료 저장 복구·최소 콘텐츠 작업 이후 [3-1절](#3-1-전투-규칙)의 발동·중첩·이동 경계와 수용 조건을 확정하고 진행한다.
